# User Profile Feature Cycle — Avatar Upload, Extended Profile Fields, Typed Identity

Scope confirmed: (1) file-upload avatars stored in Postgres, (2) extended profile fields (bio, job title, timezone, locale) in a user-scope settings section, (3) typed identity responses. Email change, notification preferences and export completion are explicitly out of scope for this cycle.

All backend work follows the house recipe (`docs/architecture/backend-refactoring-proposal.md` §"Adding a feature afterwards"): interfaces → postgres + fake + contract → migration → service → `Mount(rb)` route policy → lifecycle → fx → frontend.

---

## M1 — Avatar upload, backend

**Migration** `migrations/0043_user_avatars.up.sql` (+ `.down.sql`), marked `-- baki:compat expand`:
```sql
CREATE TABLE user_avatars (
    user_id    TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    mime_type  TEXT NOT NULL,          -- 'image/png' | 'image/jpeg'
    bytes      BYTEA NOT NULL,
    byte_size  INTEGER NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```
RLS: SELECT permitted to any authenticated user (avatars of comment authors/org peers are shown cross-user); INSERT/UPDATE/DELETE owner-only — mirror the policy style used by existing per-user tables in `internal/storage/database/rls.go`.

**Storage contract** — extend `UserStore` in `internal/storage/interfaces/users.go`:
- `SaveUserAvatar(ctx, userID, mimeType string, data []byte) error` (upsert)
- `LoadUserAvatar(ctx, userID) (*UserAvatar, error)` — `ErrNotFound` when none; `UserAvatar{MimeType, Data []byte, UpdatedAt}` (UpdatedAt doubles as the ETag source)
- `DeleteUserAvatar(ctx, userID) error`

Implement in `internal/storage/database/postgres_users.go` (new section in that file), fake methods in `internal/testutil/fakebackend.go`, contract scenarios in `internal/storage/contract/` (round-trip, ErrNotFound, idempotent delete, and FK-cascade removal in the DeleteUser erasure scenario). Note: settings tables carry no RLS because they're own-scope; avatars differ because they're read cross-user — that's why the RLS policy above.

**Service** — avatar save/delete lives on `AuthService` next to `UpdateProfile` (`internal/service/auth.go`): it owns validation and publishes audit (`audit.ActionProfileUpdate`, resource `user`, detail `avatar`), reusing the existing audit plumbing. No new domain event this cycle (profile changes were never broadcast; note as future work if realtime profile sync is wanted).

**API** — extend `AuthHandler.Mount` in `internal/api/auth.go` (plus a new `handleUserProfileAvatar` section, following the typed-endpoint conventions from `docs/architecture/api-conventions.md`):
- `POST /api/auth/profile/avatar` — multipart field `avatar`. `http.MaxBytesReader` cap 5 MB. Never trust the declared content type: sniff magic bytes; accept **PNG and JPEG only** (client canvas-resize converts webp/gif sources — avoids a webp decoder). Decode with stdlib `image` to verify it's a real image, then **re-encode** (strips EXIF/GPS — privacy win) and reject stored payloads > 512 KB / > 512 px max dimension; if `golang.org/x/image` is already in the module graph (fpdf likely pulls it) use `x/image/draw` to downscale server-side, otherwise rely on mandatory client-side resize and reject oversize inputs. On success, set `users.avatar_url` to `/api/users/{id}/avatar` (single source of truth — an upload overwrites an external URL; the frontend warns).
- `DELETE /api/auth/profile/avatar` — deletes the row and clears `avatar_url`.
- `GET /api/users/{id}/avatar` — serves bytes for any authenticated caller: `Content-Type`, `ETag` from `updated_at`, `Cache-Control: private, max-age=86400`, 404 when none. **No anonymous access and no `?token=`** — the frontend fetches with Bearer and caches (M4), keeping the avatar route inside the normal auth surface.
- Route policy via the Builder: `AuthRequired`, Scope `write` for POST/DELETE and `read` for GET, `RateUpload` bucket for the POST, `TxRequest`, `Modes(Cloud)` (desktop local mode has no user rows — the profile page shows `LocalModeCard` there; unchanged).

**Erasure/export** — FK cascade removes the avatar in `DeleteUser` (covered by the contract scenario above); include the avatar as base64 in `UserDataExport`/`ExportUserDataTo` (it is personal data). Update the streamed-export golden if one exists.

## M2 — Extended profile fields (settings section)

- `core/models/settings.go`: new top-level `Profile ProfileSettings \`json:"profile"\`` on `AppSettings` — `ProfileSettings{Bio string ≤500; JobTitle string ≤100; Timezone string (IANA); Locale string (BCP-47)}`, all empty-string defaults in `DefaultSettings()`; value struct, so `Clone()` needs no change.
- `internal/storage/settingsdoc/sections.go`: register `Section{Key: "profile", Version: 1}` with the ownership comment ("the user's identity card"). Per ADR 0012: zero-value fields need no version bump and the legacy blob path carries it automatically — no upgrade code.
- Server-side validation of the profile section on save (length caps; `time.LoadLocation` for timezone; locale against the i18n language list) wherever settings documents are validated on the write path (`internal/api/handlers_system.go` / settings service) — dual-layer with the frontend, per `frontend/src/form-validation.md`. During implementation, check whether a language/locale setting already exists in the settings document to avoid two sources of truth for locale; if one exists, reuse that key instead of adding `Locale`.
- `/me` merges the caller's profile section (one settings read) into the response below.

## M3 — Typed identity responses

- Replace the `map[string]string` in `handleAuthMe` (`internal/api/auth.go:430`) with a typed `MeResponse`: `{id, email, role, displayName, avatarUrl, createdAt, emailVerified, profile{bio, jobTitle, timezone, locale}}`. Keep the local-mode branch shape-compatible.

## M4 — Frontend

- **Avatar cache**: new `frontend/src/lib/avatarCache.ts` — bearer-authenticated fetch → `Blob` → object URL, cached per `userId` keyed by ETag, evicted entries revoke their object URL. `Avatar` (`frontend/src/components/shared/Avatar.tsx`) resolves uploaded avatars through the cache first, falls back to external `avatarUrl`, then initials (existing onError fallback unchanged).
- **`ProfileSection.tsx`**: avatar picker — file input (`accept="image/png,image/jpeg"`), client-side canvas downscale to ≤512 px + re-encode before upload, live preview, Remove button, drag-drop if cheap; the external-URL field stays as an advanced option with a note that uploading replaces it. New upload/delete methods on `authApi`. Follow form-validation conventions: constraints in `frontend/src/lib/constraints.ts`, error keys via i18n `auth` namespace.
- **Profile fields UI**: bio (textarea), job title, timezone (select from `Intl.supportedValuesOf('timeZone')`), locale — persisted through the existing per-user settings persistence (`settingsStore` / `useSettingsPersistence`), validated with the same dual-layer rules; surfaced on the profile page via `/me`.
- Unit tests colocated (`*.test.tsx`); i18n keys for all new copy.

## Key decisions & risks
- Postgres bytea over filesystem/blob: identical behavior across all deployment modes, RLS-compatible, and stays correct when Phase 5b adds replicas (no shared volume).
- Server re-encodes every upload (EXIF stripped, payload normalized, ≤512 KB / 512 px); PNG+JPEG only, magic-byte sniffed — no webp decoder dependency.
- Avatars never exposed unauthenticated; no token-in-URL pattern spread beyond `/api/events`.
- One source of truth for the rendered avatar: `avatar_url` points at the internal route after upload.
- Out of scope, noted for a later cycle: email change flow, notification preferences, personal-export completion (Phase 3 open items), showing profile fields on other users' cards (needs a directory/user-card endpoint).
