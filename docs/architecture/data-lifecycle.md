# Data lifecycle

What the data-subject export, account erasure, organisation deletion and the retention sweep do with each table (ADR 0011). Declarations in `internal/storage/database/lifecycle_<domain>.go`; runners in `lifecycle_export.go`, `lifecycle_erase.go`, `lifecycle_purge.go`.

## Adding a table

`TestPostgres_Lifecycle_EveryTableClaimed` fails until the table has a `tableClaim`: `export`/`noExport` (the `UserDataExport` key carrying the user's rows, or why the bundle has none), `erase` (`erasedByStep` — add an erase step; `erasedByCascade` — an ON DELETE CASCADE FK to `users` or to something erasure deletes; or `notPersonal` with the reason), `org` (`orgNotKeyed`, `orgByStep`, `orgByCascade`, or `orgKept` with the reason), `noPurge` (why the sweep leaves it alone; empty when you add a purge step and a `PurgeResult` field), `legacy` (the migrator step that fills it). A table holding a user's id or email without a cascading FK needs an erase step: `erasePersonal` (delete the user's own rows) or `eraseIdentity` (clear the identity on rows kept for others); seed the table in `TestPostgres_Lifecycle_ErasureSweep`, which searches every column afterwards. The fake mirrors every step, and the storage contract (`contract/lifecycle.go`) holds the fake and Postgres to the same outcomes.

## What each operation does

- **Export** (`ExportUserData`): the account, the owned flows with content, settings, the avatar image, the whole audit history, API tokens, chat on the owned flows, the user's own comments (on any flow) and triage decisions on the owned flows, organisations with own membership, sessions, the personal Azure registry (no secrets). Flows shared with the user and other members' data stay out; any read error fails the export.
- **Account erasure** (`DeleteUser`, between `AccountLifecycleService`'s prepare and finalize): conversations of the owned flows, the owned flows with their cascades, per-user rows, then the account. On rows kept for others identity is cleared (comment author — the panel then reads "A former member"; triage updater and assignee; version and baseline creator; share-link creator; invitation inviter; org owner; the minter/editor of org credentials), and a notification naming the user exactly says "a teammate". The audit trail keeps its rows: the user's own actions lose email, IP, token and user agent; rows about the user lose the user agent; a failed login loses the address; rows written after the deletion request carry no actor (`audit.WithErasedActor`). Lent org credentials are disabled by finalize; org-billed AI usage stays the organisation's, personal usage is deleted.
- **Organisation deletion** (`DeleteOrg`): the knowledge base, policies, channels and custom rules (their FKs cascade since 0048), then the row (members, invitations, settings, credentials, Azure registry cascade); its flows become their owners' own. Usage, alerts and the audit trail keep the id.
- **Retention sweep** (`PurgeExpiredData`; cloud and local+db with `PAD_AUTH_ENABLED`): expired sessions, tokens, invitations and share links; org CI credentials 30 days after expiry (listed until then); the token blacklist, idempotency keys and CI webhook delivery records older than an hour; flow snapshots older than 24 h (reads hide them at once); and, with a window, the audit trail, analysis history, usage, alerts and rule notices older than `PAD_AUDIT_RETENTION_DAYS` — 400 days by default in the cloud profile (the first sweep after an upgrade deletes older rows, in batches), none in local mode, an explicit `0` keeps everything. Unbounded tables delete 5000 rows per statement by `ctid` (`purgeStep.batched`): the batched ones above, every windowed table, sessions and rule notices; the small tables go in one statement.

The erasure and deletion statements, and the export's comment read, run without the row-level-security user (`asSystem`): keyed by one id the caller is authorised for, they must reach its rows on any flow.

## Undo ring (`flow_snapshots`, migration 0045)

The pre-mutation source that a fix, batch fix, save or restore replaced. A table, not Redis (whole sources, tens of KB to MB, TOAST-compressed; the deployment's Redis evicts under `volatile-lru`), used only where `capability.Of(cfg)` has `server-store` (`di.snapshotStoreOptions` wires `service.WithSnapshotStore`); the desktop and a service built without a store keep the in-memory ring. Bounds: the newest 20 per flow (each at most 32 MiB of stored text), and per user (migration 0047, `user_id` from the request's actor; '' for a job) the newest 200 snapshots within 128 MiB across the user's flows (`service.maxUserSnapshots`, `maxUserSnapshotBytes` — constants, not settings; per user, not per org, so one member's edits cannot evict the others' undo). A snapshot over a byte bound is refused and evicts nothing; both bounds apply in the statement that follows the insert. Rows older than 24 h (`FlowSnapshotTTL`) are hidden at once and swept. The push joins the request's transaction under a savepoint and is never fatal: a rollback takes the snapshot with it, a failed push leaves the mutation intact. Tenancy: the flow-child RLS policy (migration 0034) — a row is reachable when its flow is; a restore loads by `(flow_id, id)`, so another flow's id restores nothing (404). `ON DELETE CASCADE` takes the ring with its flow; erasure clears `user_id` on rows that stay with other people's flows; not in the export bundle (a day-old copy of the exported source).

## Integrity constraints (migration 0048)

Foreign keys back what deletion did by hand: `knowledge_documents`, `policies`, `org_channels` and `org_custom_rules` reference `organisations (id)`, and `refresh_tokens` references `users (id)`, all `ON DELETE CASCADE`; a knowledge chunk references its document by `(doc_id, org_id)` (unique index on `(id, org_id)`), scoping chunks to their document's org. Deliberately unconstrained: `org_members.user_id` (the `local` member has no `users` row) and `conversations.flow_id` (legacy chats about files that were never flows). One account per email whatever its case (`users_lower_email_key`), one invitation per token (`org_invites_token_hash_key`). `share_tokens.created_by` and `policies.description` are `NOT NULL`; an id-less policy gets a generated id (`RekeyIdlessPolicy`). The step deletes orphan policies, channels and custom rules and raises the counts as Postgres notices (the Postgres server log: `docker compose logs db`; not the app log). Growing tables' orphans (documents of deleted orgs, chunks under other orgs, erased accounts' sessions) are cleaned up by `schema_upkeep` before validating keys. The step adds foreign keys `NOT VALID`, and refuses case-duplicate emails or duplicate invite tokens (remedy in [deployment.md](../deployment.md#before-deploying-v48)). `expand`: an image rollback needs no down; `bakicli migrate down 47` (run with the release that contains the steps; the image ships no bakicli, use the release artifact or `go run ./cmd/bakicli` from that checkout) removes constraints and indexes. The fake refuses the same orphans (`contract/integrity.go`).
