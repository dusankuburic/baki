# DI wiring: constructors, and the setters that remain

The backend is wired with fx in `internal/di` (services, api) and `internal/app`. A service takes its dependencies through its constructor; a post-construction setter (`SetX`/`OnX`) is allowed only for a **cycle** (no extraction breaks it yet), an **event hook** (replaced by an `fx.Invoke` subscription), or a **deferral** (moving the dependency touches many test call sites; converted when the code is next touched). `TestDISetters_Listed` pins every setter with its reason — a new one fails the test until listed; a removed one fails until its entry goes. When two services need each other, extract the part both need, as `service.AIBudget` (the daily budget rule and in-flight ledger, taken by `NewChatService`, `rag.NewKnowledgeService` and the provider factory as its `ai.BudgetChecker`) and `service.FlowScopeResolver` (library scopes, taken by `NewLibraryService` and `NewDashboardService`) were.

Setters that remain in `internal/di`: `factory.SetEmbeddingDimensions` (configures the object its own provider builds, ~65 test call sites), `src.SetAzureExportConfigSource` (a cycle: the export reads Azure connection configs from a service built on the backend) and `FlowService.SetRuleProfileResolver` (deferred, ~55 test call sites).

## What only the database offers: fx values, not type assertions

`internal/app`'s `provideStorageBackend` provides the backend and, beside it, each database-only capability as an fx value of its own, nil without a database (ADR 0010): the cross-replica lock (`lock.GlobalLocker`), the pool for the token blacklist, the keystore constructor, field encryption, the audit org backfill, the blob probe, the Azure registry, and the request transaction with its Idempotency-Key store (`reqtx.Opener`, `storageif.IdempotencyStore`, nil without row-level security). A consumer takes the one it needs as a parameter and tests it for nil — nothing type-asserts the backend (`TestArch_StorageTypeAssertionsRatchet`); test graphs add `noDatabase()`. The keystore works the same way: `provideKeyStore` provides the keys and, only with the encrypted database keystore, the org credential store (`service.OrgKeyStore`), the key-family lister and the rotation re-seal pass (`storagedb.KeyResealer`), nil with the OS keyring (test graphs add `fakeKeyStore()`). The roles every backend has are not fx values: services take the backend through the narrow role interface in their constructor.

## Wiring outside `internal/di` (not ratcheted)

`provideScanner`'s `scanner.Set*` calls (deferred; its cross-replica lock already is a parameter), `api.NewRouter`'s `EventManager.SetOriginChecker`/`SetClientKeyFunc`/`SetRevocationChecker` (the router owns those policies), `ProvideAI`'s `ai.Configure*` egress settings, and `initLogger`'s process-wide `Set*` calls (`lifecycle.SetInstanceID`, `errreport.SetInstanceID`, the panic hook) — each set once at boot.

## The application: `internal/app`

`main.go` keeps only what must stay in package `main` — the swag general-API annotations (`swag init -g main.go`), the ldflags stamps and `main()` — and is the package's only non-test file, because the Dockerfile and CI build `go build main.go` (`TestMainPackageIsMainGoAlone`). Everything else is `internal/app`, one file per concern: `app.go` (`Build`, `Options`: the stop timeout, the providers, `di.ServiceModule`, `di.APIModule`, `redisx.Module` (the optional client and its health), `invalidation.Module` (installs the fan-out as the bus's `Replicas` hook, stopped after the HTTP server), the ordered Invoke list), `config.go` (`config.Load`: `PAD_CONFIG` file, else env, else defaults), `observability.go`, `storage.go` (the backend, pool settings and metrics, the background HNSW build), `keystore.go`, `auth.go`, `governance.go` (scanner, notifier, the migration runner), `jobs_{retention,backfill,reseal}.go`, `server.go` (the listener, the desktop `CONFIG:` handshake, the OnStop sequence). A change goes to the file of its concern: the typed configuration to `config.go`/`storage.go`, a job to a `jobs_*.go` file, the drain sequence to `server.go` and its hook to the end of `app.go`'s Invoke list.

**The order is load-bearing.** fx runs stop hooks in reverse registration order and invokes module-first, then in list order. The `observability` module runs first (the logger names the replica; every line is JSON from the first, `TestApp_LogsAreJSONFromTheFirstLine`); then the modules' invokes construct storage (the migrations), the audit recorder, the auth manager and the router; then `initAuditTrail`, `initRetentionPurge`, `initFieldEncryption`, `startServer`, and after it the jobs whose stop hooks must run before the server drains the background runners. Cloud stop order: (1) re-seal, field-encryption backfill and audit backfill cancelled; (2) the scanner stops; (3) the server — SSE closed, chat streams cancelled, WebSockets drained, `http.Server.Shutdown`, `lifecycle.DrainAll`; (4) the retention loop; (5) the WebSocket hub, the blacklist cache, the audit recorder (it drains), the storage pool; (6) telemetry flushes. `TestApp_StopOrder` pins this list and the desktop one.

Tests build services with the same constructors: a zero `ChatOptions` gives the chat service a private budget over its own settings and store (a bare `&ChatService{}` builds it lazily), and a nil scope resolver passed to `NewLibraryService` builds one over the same storage and authz.
