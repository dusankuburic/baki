## How to read this

Each item is one defect or gap in the AI assistant. It says what goes wrong and when. Items are sorted into four tiers by how directly they affect a user who relies on the answer:

- **Tier 0: wrong on a normal path.** The assistant answers from the wrong facts, loses a thread or an applied fix, sends a secret to the provider, or a setting the UI offers has no effect. Nothing has to fail for these to happen. They are fixed before anything is added.
- **Tier 1: wrong when something fails.** A provider hangs or rate-limits, Redis blips, a replica dies, a call is retried, the user presses Stop, a turn runs long. These failures are expected, and the code handles them wrongly, silently, or bills them wrongly.
- **Tier 2: limits on what the assistant can do or what we can prove.** Missing tools and retrieval, configuration that is not validated, and the test harnesses (request snapshots, evals, a live smoke) that a prompt or wire change needs before anyone can judge it.
- **Tier 3: hygiene.** Documentation drift, operator surfaces, UX polish and hardening of the test suite. These are done while their files are open for a higher-tier item, or on their own when they are cheap.

**Ids.** An id has the form `R-<category>-<n>`. The category is one of `analyzer-boundary`, `approvals`, `budget`, `config`, `docs`, `frontend`, `knowledge`, `observability`, `provider`, `replicas`, `security`, `streaming`, `testing` or `tool-loop`. Ids are stable:

- An id is never renumbered or reused.
- It keeps its value when the item moves to another tier.
- A number with a `c` in it (`R-security-c13`) is an ordinary id. The letter carries no order.

Commits, PR titles and test comments name the id they close.

**Evidence.** Every item cites `file:line` as of the date in this document's byline (the ADRs' form: `Date: 2026-10-22.`, as in `docs/adr/0028-ai-budget-hook-and-provider-policy.md:3`). Line numbers drift and the code is the authority. Whoever picks up an item re-reads the cited lines first. If the defect is already gone, the item is closed in the change that notices it.

**ADRs.** Where a decision is already recorded, the item names it (for example `ADR 0026 §20` or `ADR 0028 item 1`). Either the ADR specifies behaviour the code does not implement, or it records the choice the item would revisit. An item that changes a recorded decision lands with an amendment or a new ADR in `docs/adr/`.

**Leaving the list.** An item leaves when its fix ships with its acceptance criteria as tests:

- The failure scenario the item describes becomes a test that fails before the change and passes after it.
- Every golden the change touches is refreshed with its `-update-*` flag, and the diff is reviewed (the list is in `CLAUDE.md`).
- Any document that described the old behaviour is corrected in the same change.

The item is deleted in that same change: its section from the category file under [`ai-roadmap/`](ai-roadmap/) and its row from the index below. A `docs` item leaves when the document matches the code. An item dropped without a fix leaves only with its reason recorded in an ADR.

## Where the assistant stands today

**Provider layer.** Each provider is one `ai.ProviderSpec` (`internal/ai/spec.go:215-243`), registered at init and pinned by `internal/ai/testdata/providers.golden`. `ProviderFactory.wrapChainScoped` builds the one chain every caller gets: circuit breaker, then retry, then tracing, then the audited wrapper (`internal/ai/factory.go:262-275`). The audited wrapper runs the daily-budget hook before each call. It skips that hook for alias-model providers (Azure AI Foundry) (`internal/ai/audited.go:132-146`). Retry caps its backoff at 30 s and honours `Retry-After` up to 20 s (`internal/ai/retry.go:21`, `:72`). Breaker state is a process-wide map (`internal/ai/circuitbreaker.go:46`). The shared transport sets a 30 s response-header timeout and a connection cap per host (`internal/ai/httpclient.go:40-44`), and no TLS handshake timeout. The per-process memos are declared replica-local in `internal/archtest/state_test.go:63-72`. The spec table, retry and breaker have unit tests. `httpclient.go` and `tracing.go` have none: there is no `internal/ai/httpclient_test.go` or `internal/ai/tracing_test.go`. **Tool loop and approvals.** Eight `ai.ToolSpec`s are registered (`internal/ai/tools.go:270-341`). Two of them, `apply_fix` and `apply_fixes`, need approval (`:321`, `:334`), and a per-stream `ToolGate` (`:126`) decides what is offered. The loop runs at most `maxToolIterations = 6` (`internal/service/chat.go:42`). At that limit both loops ask for one final answer with tools ruled out, an approved apply refunds its step (ten at most), and the final turn's text is the answer even beside tool calls, which are skipped and counted in a trail row; a final turn with calls and no text, or no answer at all, fails with `ChatErrToolLoopLimit`. Read-only calls run four at a time (`internal/service/chat_tool_exec.go:25`). A tool result is capped at 6000 bytes (`internal/ai/tools.go:24`). A tool gets 30 s; an approval tool has no tool deadline: its decision waits 60 s, and the apply and its verification then get 30 s plus 30 s per fix from the approval (`fixApplyTimeout`, `internal/service/chat_fixes.go`). The idle watchdog is kept alive every 15 s while a decision is pending (`internal/service/chat_approvals.go:34`). The gate offers the fix tools only to a caller who may edit the flow, and the system prompt has a variant for each tool access. A panicking tool on any path becomes an error-shaped result. `tools.golden` pins names, scopes, approval flags, descriptions and input schemas; `prompts.golden` pins the system prompts and the marker-mode instructions. No test in `internal/ai/tools*_test.go` reaches the 30 s tool-timeout branch: a search for "timed out" there finds nothing. **Budgets, pricing and cost.** A budget check adds three amounts:

## Improving the current integration

The items share a small set of causes. The themes below group them, in the order they should be tackled. A later theme relies on the safety net or the correct data that an earlier one provides.

**1. Secrets and the prompt boundary.** [R-provider-29](ai-roadmap/provider.md#r-provider-29).

The per-site gaps this theme opened with — `Block.Name`, pasted PAD code without the literal rules, the knowledge chunks stored unscrubbed, the questions stored raw — closed in step 1, and `internal/service/chat_egress_test.go` is now the one regression net under every call site (ADR 0034). The instruction/data boundary for flow-derived text closed in step 2 (ADR 0036: the data frames, the system-prompt rule, the escaping). What remains here is [R-provider-29](ai-roadmap/provider.md#r-provider-29) (the hosted-tool egress of Foundry agents), which governs the same boundary. This theme stays first because a leak cannot be recalled.

**2. What the model sees matches the flow.** [R-analyzer-boundary-5](ai-roadmap/analyzer-boundary.md#r-analyzer-boundary-5), [R-analyzer-boundary-6](ai-roadmap/analyzer-boundary.md#r-analyzer-boundary-6), [R-frontend-7](ai-roadmap/frontend.md#r-frontend-7), [R-frontend-15](ai-roadmap/frontend.md#r-frontend-15), [R-frontend-25](ai-roadmap/frontend.md#r-frontend-25), [R-tool-loop-8](ai-roadmap/tool-loop.md#r-tool-loop-8), [R-tool-loop-9](ai-roadmap/tool-loop.md#r-tool-loop-9), [R-tool-loop-10](ai-roadmap/tool-loop.md#r-tool-loop-10).

All of these concern what context and tools give the model:

- missing rule facts;
- subflows that cannot be walked;
- values trimmed to 200 characters.

The preview that was not what gets sent, the exact-match lineage, the flat 4000-token budget and the history truncation the user never saw closed in step 2, under a deterministic `BuildContext` and the request snapshot golden (`internal/service/testdata/request_snapshots/`, ADR 0035): every other fix here now shows up as a reviewable diff instead of a guess.

**3. The tool loop's limits and failure handling.** [R-tool-loop-14](ai-roadmap/tool-loop.md#r-tool-loop-14), [R-frontend-6](ai-roadmap/frontend.md#r-frontend-6), [R-frontend-16](ai-roadmap/frontend.md#r-frontend-16), [R-provider-21](ai-roadmap/provider.md#r-provider-21).

The loop's own bookkeeping was fixed in the tier-0 pass and step 3: stale memory after a fix, the cap that cut the pagination hint, the six-iteration cap, a partial `<tool_call>` taken as the answer, marker instructions without schemas, fix tools advertised where they cannot run, missing panic guards and one deadline over both the decision and the apply ([Closed in step 3](#closed-in-step-3-the-tool-loop)). What is left sits beside the loop: Copilot's missing tool capability, tools off by default ([R-frontend-6](ai-roadmap/frontend.md#r-frontend-6)), which is now safe to change, slash commands with no link to the tools, and no `tool_choice`. `FakeProvider`'s failure modes and the prompt goldens from step 3 are the tests later loop changes land against.

**4. Approvals and applied fixes survive every ending.** [R-approvals-1](ai-roadmap/approvals.md#r-approvals-1), [R-approvals-2](ai-roadmap/approvals.md#r-approvals-2), [R-approvals-4](ai-roadmap/approvals.md#r-approvals-4), [R-approvals-5](ai-roadmap/approvals.md#r-approvals-5), [R-approvals-7](ai-roadmap/approvals.md#r-approvals-7), [R-approvals-8](ai-roadmap/approvals.md#r-approvals-8), [R-approvals-10](ai-roadmap/approvals.md#r-approvals-10), [R-approvals-11](ai-roadmap/approvals.md#r-approvals-11), [R-approvals-c17](ai-roadmap/approvals.md#r-approvals-c17), [R-approvals-c9](ai-roadmap/approvals.md#r-approvals-c9), [R-frontend-8](ai-roadmap/frontend.md#r-frontend-8), [R-frontend-9](ai-roadmap/frontend.md#r-frontend-9), [R-security-4](ai-roadmap/security.md#r-security-4), [R-streaming-2](ai-roadmap/streaming.md#r-streaming-2), [R-testing-3](ai-roadmap/testing.md#r-testing-3), [R-testing-7](ai-roadmap/testing.md#r-testing-7), [R-testing-14](ai-roadmap/testing.md#r-testing-14), [R-docs-5](ai-roadmap/docs.md#r-docs-5).

An approved fix changes the user's flow. Whatever happens next must not lose that change or misreport it: a Stop, a drain, a re-minted block id, a version conflict, a desktop restart, a read-only flow, a long journal. The thread now keeps its flow and its context block across a fix (the desktop flow identity and the content anchor of the tier-0 pass). [R-testing-3](ai-roadmap/testing.md#r-testing-3) adds a shared event fixture, and [R-testing-7](ai-roadmap/testing.md#r-testing-7) an approval test at the router. Both must exist before the approval card's payload grows a server deadline, a diff or a risk signal ([R-approvals-1](ai-roadmap/approvals.md#r-approvals-1), [R-approvals-7](ai-roadmap/approvals.md#r-approvals-7)).

**5. Settings and credentials that take effect.** [R-config-2](ai-roadmap/config.md#r-config-2), [R-config-3](ai-roadmap/config.md#r-config-3), [R-config-4](ai-roadmap/config.md#r-config-4), [R-provider-2](ai-roadmap/provider.md#r-provider-2), [R-provider-18](ai-roadmap/provider.md#r-provider-18), [R-provider-19](ai-roadmap/provider.md#r-provider-19), [R-provider-22](ai-roadmap/provider.md#r-provider-22), [R-provider-27](ai-roadmap/provider.md#r-provider-27), [R-provider-28](ai-roadmap/provider.md#r-provider-28), [R-provider-30](ai-roadmap/provider.md#r-provider-30), [R-frontend-10](ai-roadmap/frontend.md#r-frontend-10), [R-security-7](ai-roadmap/security.md#r-security-7), [R-security-8](ai-roadmap/security.md#r-security-8), [R-observability-17](ai-roadmap/observability.md#r-observability-17), [R-docs-9](ai-roadmap/docs.md#r-docs-9).

In each case the UI or the API reports a state the server does not have. An empty key counts as "configured". An unreadable keyring reads as "no key". A failed save rolls back silently. The deployment's `ai.*` writer (`PUT /api/admin/settings/ai`) and the device-flow refusal shipped in the tier-0 pass; [R-config-2](ai-roadmap/config.md#r-config-2) validates the rest of the `ai` section behind that writer.

**6. Provider error classification and transport limits.** [R-provider-3](ai-roadmap/provider.md#r-provider-3), [R-provider-4](ai-roadmap/provider.md#r-provider-4), [R-provider-5](ai-roadmap/provider.md#r-provider-5), [R-provider-6](ai-roadmap/provider.md#r-provider-6), [R-provider-7](ai-roadmap/provider.md#r-provider-7), [R-provider-10](ai-roadmap/provider.md#r-provider-10), [R-provider-11](ai-roadmap/provider.md#r-provider-11), [R-provider-12](ai-roadmap/provider.md#r-provider-12), [R-provider-25](ai-roadmap/provider.md#r-provider-25), [R-provider-c2](ai-roadmap/provider.md#r-provider-c2), [R-provider-c3](ai-roadmap/provider.md#r-provider-c3), [R-provider-c5](ai-roadmap/provider.md#r-provider-c5), [R-streaming-1](ai-roadmap/streaming.md#r-streaming-1), [R-streaming-10](ai-roadmap/streaming.md#r-streaming-10), [R-provider-16](ai-roadmap/provider.md#r-provider-16), [R-config-5](ai-roadmap/config.md#r-config-5), [R-config-6](ai-roadmap/config.md#r-config-6), [R-docs-3](ai-roadmap/docs.md#r-docs-3).

Retry, the breaker, the watchdog and the user's error bubble all depend on how a failure is classified, and the classification is uneven:

- a hung upstream is invisible to both retry and breaker;

- **R-security-c11, R-security-c12.** One table of secret classes (`core/ai/scrubber/classes.go`: JSON- and YAML-quoted values, `password:` values with symbols, Basic auth, `sk-` keys, real GitLab tokens, `x-functions-key`, URL userinfo and credential query parameters such as `sig=` and `code=`) drives both the text scrubber and the stream scrubber, whose anchors, viability and terminal states are derived from it. The context scrub covers the finding-metadata channel. After the review: a URL-parameter, Basic, JWT or symbol-value hold drains past the hold cap instead of releasing the credential's tail; the URL-parameter hold starts at the `?` or `&`, so the parameters after a token survive, and `;` ends a value (SAS connection strings); prose after a keyword is kept (`looksLikeSymbolCredential`: a value starts alphanumeric and carries no `://`, `Authorization: Basic` needs a decodable `user:pass`, and a `%Var%` or `${VAR}` reference is left alone).
