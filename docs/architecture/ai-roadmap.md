## How to read this

Each item is one defect or gap in the AI assistant. It says what goes wrong and when. Items are sorted into four tiers by how directly they affect a user who relies on the answer:

- **Tier 0: wrong on a normal path.** The assistant answers from the wrong facts, loses a thread or an applied fix, sends a secret to the provider, or a setting the UI offers has no effect. Nothing has to fail for these to happen. They are fixed before anything is added.
- **Tier 1: wrong when something fails.** A provider hangs or rate-limits, Redis blips, a replica dies, a call is retried, the user presses Stop, a turn runs long. These failures are expected, and the code handles them wrongly, silently, or bills them wrongly.
- **Tier 2: limits on what the assistant can do or what we can prove.** Missing tools and retrieval, configuration that is not validated, and the test harnesses (request snapshots, evals, a live smoke) that a prompt or wire change needs before anyone can judge it.
- **Tier 3: hygiene.** Documentation drift, operator surfaces, UX polish and hardening of the test suite. These are done while their files are open for a higher-tier item, or on their own when they are cheap.

**Ids.** An id has the form `R-<category>-<n>`. The category is one of `analyzer-boundary`, `approvals`, `budget`, `config`, `docs`, `frontend`, `knowledge`, `observability`, `provider`, `replicas`, `security`, `streaming`, `testing` or `tool-loop`. Ids are stable:

- An id is never renumbered or reused.
- It keeps its value when the item moves to another tier.
- A number with a `c` in it (`R-security-c13`) is an ordinary id. The letter carries no order.

Commits, PR titles and test comments name the id they close.

**Evidence.** Every item cites `file:line` as of the date in this document's byline (the ADRs' form: `Date: 2026-10-22.`, as in `docs/adr/0028-ai-budget-hook-and-provider-policy.md:3`). Line numbers drift and the code is the authority. Whoever picks up an item re-reads the cited lines first. If the defect is already gone, the item is closed in the change that notices it.

**ADRs.** Where a decision is already recorded, the item names it (for example `ADR 0026 §20` or `ADR 0028 item 1`). Either the ADR specifies behaviour the code does not implement, or it records the choice the item would revisit. An item that changes a recorded decision lands with an amendment or a new ADR in `docs/adr/`.

**Leaving the list.** An item leaves when its fix ships with its acceptance criteria as tests:

- The failure scenario the item describes becomes a test that fails before the change and passes after it.
- Every golden the change touches is refreshed with its `-update-*` flag, and the diff is reviewed (the list is in `CLAUDE.md`).
- Any document that described the old behaviour is corrected in the same change.

The item is deleted in that same change: its section from the category file under [`ai-roadmap/`](ai-roadmap/) and its row from the index below. A `docs` item leaves when the document matches the code. An item dropped without a fix leaves only with its reason recorded in an ADR.

## Where the assistant stands today

**Provider layer.** Each provider is one `ai.ProviderSpec` (`internal/ai/spec.go:215-243`), registered at init and pinned by `internal/ai/testdata/providers.golden`. `ProviderFactory.wrapChainScoped` builds the one chain every caller gets: circuit breaker, then retry, then tracing, then the audited wrapper (`internal/ai/factory.go:262-275`). The audited wrapper runs the daily-budget hook before each call. It skips that hook for alias-model providers (Azure AI Foundry) (`internal/ai/audited.go:132-146`). Retry caps its backoff at 30 s and honours `Retry-After` up to 20 s (`internal/ai/retry.go:21`, `:72`). Breaker state is a process-wide map (`internal/ai/circuitbreaker.go:46`). The shared transport sets a 30 s response-header timeout and a connection cap per host (`internal/ai/httpclient.go:40-44`), and no TLS handshake timeout. The per-process memos are declared replica-local in `internal/archtest/state_test.go:63-72`. The spec table, retry and breaker have unit tests. `httpclient.go` and `tracing.go` have none: there is no `internal/ai/httpclient_test.go` or `internal/ai/tracing_test.go`. Items: [R-config-5](ai-roadmap/config.md#r-config-5), [R-config-6](ai-roadmap/config.md#r-config-6), [R-replicas-8](ai-roadmap/replicas.md#r-replicas-8), [R-observability-10](ai-roadmap/observability.md#r-observability-10).

**Provider implementations.** Five providers share `openaiBase`. Its `sendWith` (`internal/ai/openai_compat.go:190`) repairs a refused request parameter once and memoises the repair. Claude and Gemini have their own wires. Gemini classifies an error only when the response body parses as JSON. A bodyless or HTML 429 or 5xx therefore falls through to a plain `gemini API error (status N)`, which is neither retried nor counted by the breaker (`internal/ai/gemini.go:360-383`). Azure AI Foundry is the largest surface: one provider routes a model id to chat completions, the Responses API or the Anthropic route (`internal/ai/azure_foundry.go:321`). Wire tests are `httptest` stubs with inline SSE strings. GitHub device auth has no test file: there is no `internal/ai/github_auth_test.go`. Items: [R-provider-20](ai-roadmap/provider.md#r-provider-20), [R-provider-21](ai-roadmap/provider.md#r-provider-21), [R-provider-22](ai-roadmap/provider.md#r-provider-22), [R-tool-loop-14](ai-roadmap/tool-loop.md#r-tool-loop-14), [R-docs-3](ai-roadmap/docs.md#r-docs-3).

**Streaming, tokens and context windows.** The raw providers turn four SSE dialects into one `ai.Chunk` stream. The Gemini parser (`internal/ai/stream.go:807`) has no keepalives, no served model and no mid-stream error handling. When a provider reports no usage, the fallback estimate counts the system prompt, the message contents and the tool-call arguments, but not `req.Tools` (`internal/ai/audited.go:397-416`). `ai_request_duration_seconds` uses `prometheus.DefBuckets` (`internal/ai/metrics.go:25-31`), whose largest bucket is 10 s, shorter than most streams. The in-flight reservation assumes 4096 output tokens when the request sets no cap (`internal/service/chat.go:103-108`). The idle watchdog allows 90 s of silence, or 5 minutes during a hosted step (`internal/service/chat_resume.go:50`, `:55`). The exact-prefix truncation tests skip when the cl100k tokenizer cannot load (`internal/ai/tokens_truncate_test.go:43-50`). Items: [R-testing-18](ai-roadmap/testing.md#r-testing-18), [R-frontend-27](ai-roadmap/frontend.md#r-frontend-27).

**Tool loop and approvals.** Eight `ai.ToolSpec`s are registered (`internal/ai/tools.go:270-341`). Two of them, `apply_fix` and `apply_fixes`, need approval (`:321`, `:334`), and a per-stream `ToolGate` (`:126`) decides what is offered. The loop runs at most `maxToolIterations = 6` (`internal/service/chat.go:42`). At that limit both loops ask for one final answer with tools ruled out, an approved apply refunds its step (ten at most), and the final turn's text is the answer even beside tool calls, which are skipped and counted in a trail row; a final turn with calls and no text, or no answer at all, fails with `ChatErrToolLoopLimit`. Read-only calls run four at a time (`internal/service/chat_tool_exec.go:25`). A tool result is capped at 6000 bytes (`internal/ai/tools.go:24`). A tool gets 30 s; an approval tool has no tool deadline: its decision waits 60 s, and the apply and its verification then get 30 s plus 30 s per fix from the approval (`fixApplyTimeout`, `internal/service/chat_fixes.go`). The idle watchdog is kept alive every 15 s while a decision is pending (`internal/service/chat_approvals.go:34`). The gate offers the fix tools only to a caller who may edit the flow, and the system prompt has a variant for each tool access. A panicking tool on any path becomes an error-shaped result. An approved fix finds its finding again on the flow as it is at the approval, retries a version conflict once, and reports a failure in words the model can act on. While the server drains no approval is asked or approved, and a Stop or the server's stop waits for an approved apply. Decisions and applied fixes leave audit rows (`chat.fix_decision`, `flow.fix_apply`). `tools.golden` pins names, scopes, approval flags, descriptions and input schemas; `prompts.golden` pins the system prompts and the marker-mode instructions. No test in `internal/ai/tools*_test.go` reaches the 30 s tool-timeout branch: a search for "timed out" there finds nothing. Items: [R-tool-loop-8](ai-roadmap/tool-loop.md#r-tool-loop-8), [R-tool-loop-9](ai-roadmap/tool-loop.md#r-tool-loop-9), [R-tool-loop-10](ai-roadmap/tool-loop.md#r-tool-loop-10), [R-approvals-1](ai-roadmap/approvals.md#r-approvals-1), [R-approvals-7](ai-roadmap/approvals.md#r-approvals-7), [R-approvals-8](ai-roadmap/approvals.md#r-approvals-8), [R-approvals-9](ai-roadmap/approvals.md#r-approvals-9), [R-approvals-10](ai-roadmap/approvals.md#r-approvals-10), [R-approvals-11](ai-roadmap/approvals.md#r-approvals-11), [R-approvals-12](ai-roadmap/approvals.md#r-approvals-12), [R-frontend-16](ai-roadmap/frontend.md#r-frontend-16).

**Chat service: streams, conversations and resume.** `ChatService.StreamChatMessage` (`internal/service/chat.go:675`) validates the request, reserves budget and a stream slot, and hands the turn to a worker. The worker runs a plain stream, the native tool loop (`:1156`) or the prompt-marker loop (`:1374`). Stored conversations change through `mutateConversation`, a read-change-compare-and-swap loop (`internal/service/chat_conversation_version.go:107`). Output is batched into 16 ms chunk events (`internal/service/chat_scrubber.go:17`). A mirror loop copies the stream to Redis for resume (`internal/service/chat_resume.go:266`). The versioning tests run on the fake backend (`internal/service/chat_conversation_version_test.go:27`), and the Redis tests run on miniredis (`internal/service/chat_resume_test.go:71`). Real Postgres compare-and-swap and real Redis behaviour are therefore not exercised at the service level. Items: [R-replicas-2](ai-roadmap/replicas.md#r-replicas-2), [R-replicas-3](ai-roadmap/replicas.md#r-replicas-3), [R-replicas-4](ai-roadmap/replicas.md#r-replicas-4), [R-replicas-6](ai-roadmap/replicas.md#r-replicas-6), [R-replicas-11](ai-roadmap/replicas.md#r-replicas-11), [R-streaming-4](ai-roadmap/streaming.md#r-streaming-4), [R-streaming-c8](ai-roadmap/streaming.md#r-streaming-c8), [R-frontend-22](ai-roadmap/frontend.md#r-frontend-22).

**Budgets, pricing and cost.** A budget check adds three amounts:

- today's recorded spend, a `SUM(estimated_cost)` from `date_trunc('day', now())` in the session timezone (`internal/storage/database/postgres_users.go:1024-1034`);
- the caller's in-flight cost;
- the other running streams' reservations, read from a `spendLedger` (`internal/service/ai_budget.go:33`).

The ledger is in-process (`memLedger`, `:42`) unless `PAD_MAX_REPLICAS > 1` (`internal/di/services.go:235`). The daily-usage read is memoised for the whole request by `ai.BudgetMemo` (`internal/ai/budget.go:62-85`). Alias-model spend is never gated (`internal/ai/audited.go:133`). The ledger and the hook have tests, but on miniredis and the fake backend only. `docs/architecture/ai-providers.md:21` says a running stream stops at its next re-check. That holds only for tool-loop streams. Items: [R-replicas-c23](ai-roadmap/replicas.md#r-replicas-c23), [R-observability-3](ai-roadmap/observability.md#r-observability-3).

**Organisation knowledge.** An admin uploads `.txt`/`.md` files. The text is cut into 1000-rune chunks (`internal/rag/service.go:1051`) with 15% overlap (`:1109`), embedded, and searched through a pgvector HNSW iterative scan (`internal/storage/database/postgres_knowledge.go:307-325`). Re-index stops at 10 000 chunks (`internal/rag/service.go:70`). A chat turn waits at most 800 ms for guidelines (`internal/service/chat_context.go:33`) from `KnowledgeService.Search` (`internal/rag/service.go:661`), then proceeds without them. The rag package has identity and resume tests. No Playwright spec covers the Knowledge Base panel: the only "knowledge" hit in `frontend/e2e/` is unrelated, in `frontend/e2e/home-dashboard.spec.ts:98`. Items: [R-knowledge-13](ai-roadmap/knowledge.md#r-knowledge-13), [R-observability-6](ai-roadmap/observability.md#r-observability-6).

**Frontend chat.** One app-root engine, `ChatStreamProvider` (`frontend/src/App.tsx:361`), owns every stream. It subscribes to `chat:event` frames, watches the SSE connection for 45 s of silence (`frontend/src/api/client.ts:514`), and registers streams with the begin handshake off (`frontend/src/components/chat/hooks/stream-engine/lifecycle.ts:210`). `ChatMessageList.tsx` and `ChatUsageMeter.tsx` have no test files. The streaming e2e pins `crypto.randomUUID` (`frontend/e2e/chat-stream.spec.ts:31-34`), so it never asserts the assistant's reply. Items: [R-frontend-21](ai-roadmap/frontend.md#r-frontend-21), [R-frontend-c7](ai-roadmap/frontend.md#r-frontend-c7), [R-frontend-c24](ai-roadmap/frontend.md#r-frontend-c24), [R-testing-13](ai-roadmap/testing.md#r-testing-13).

**Configuration and credentials.** With a database and a key, credentials live in `EncryptedKeyStore`, AES-256-GCM in Postgres (`internal/storage/database/keystore.go:23-36`). Otherwise they live in the OS keyring. Since step 5 a key is checked before it is stored, the `ai` section of a settings write is checked against its caps, the client posts only the sections it changed, and a credential the keystore cannot decrypt is reported as unreadable (ADR 0040). Six specs besides Azure declare `CapOrgShared` (`internal/ai/spec_claude.go:9` and the other `spec_*.go`). Organisation credentials, however, have routes only for Azure (`internal/api/org_azure.go:48-126`). Items: [R-provider-27](ai-roadmap/provider.md#r-provider-27), [R-provider-28](ai-roadmap/provider.md#r-provider-28), [R-security-8](ai-roadmap/security.md#r-security-8), [R-observability-17](ai-roadmap/observability.md#r-observability-17), [R-docs-9](ai-roadmap/docs.md#r-docs-9).

**The analyzer-to-assistant seam.** Fix flags mark which fixes change behaviour and which read the finding's variable or property (`core/analyzer/fix_dispatch.go:27-36`). A chat-approved fix is applied to the real flow with `unsafe=false` (`internal/service/chat_fixes.go:295-298`), so a fix flagged as behaviour-changing is refused in chat. `BuildContext` is deterministic since step 2, and the assembled request is pinned by `internal/service/testdata/request_snapshots/`. The browser test of the findings apply path skips every step whose button is absent (`frontend/e2e/apply-fix.spec.ts:57-62`), so it passes without applying anything. Items: [R-analyzer-boundary-5](ai-roadmap/analyzer-boundary.md#r-analyzer-boundary-5), [R-analyzer-boundary-6](ai-roadmap/analyzer-boundary.md#r-analyzer-boundary-6), [R-frontend-9](ai-roadmap/frontend.md#r-frontend-9), [R-frontend-15](ai-roadmap/frontend.md#r-frontend-15), [R-frontend-25](ai-roadmap/frontend.md#r-frontend-25), [R-testing-14](ai-roadmap/testing.md#r-testing-14), [R-docs-5](ai-roadmap/docs.md#r-docs-5).

**Testing and operation.** `internal/ai` has 671 `Test`/`Benchmark` functions, and `internal/service` has 61 `chat_*_test.go` files. `internal/ai/testdata` holds only `providers.golden` and `tools.golden`: there is no recorded wire corpus. ## Improving the current integration

The items share a small set of causes. The themes below group them, in the order they should be tackled. A later theme relies on the safety net or the correct data that an earlier one provides.

**1. Secrets and the prompt boundary.** Closed.

The per-site gaps this theme opened with — `Block.Name`, pasted PAD code without the literal rules, the knowledge chunks stored unscrubbed, the questions stored raw — closed in step 1, and `internal/service/chat_egress_test.go` is now the one regression net under every call site (ADR 0034). The instruction/data boundary for flow-derived text closed in step 2 (ADR 0036: the data frames, the system-prompt rule, the escaping). The hosted-tool egress of Foundry agents closed in phase 2 ([Closed in phase 2](#closed-in-phase-2-security-and-data-integrity)): an agent's hosted tools are audited per turn and the caveat is documented.

**2. What the model sees matches the flow.** [R-analyzer-boundary-5](ai-roadmap/analyzer-boundary.md#r-analyzer-boundary-5), [R-analyzer-boundary-6](ai-roadmap/analyzer-boundary.md#r-analyzer-boundary-6), [R-frontend-15](ai-roadmap/frontend.md#r-frontend-15), [R-frontend-25](ai-roadmap/frontend.md#r-frontend-25), [R-tool-loop-8](ai-roadmap/tool-loop.md#r-tool-loop-8), [R-tool-loop-9](ai-roadmap/tool-loop.md#r-tool-loop-9), [R-tool-loop-10](ai-roadmap/tool-loop.md#r-tool-loop-10).

All of these concern what context and tools give the model:

- missing rule facts;
- subflows that cannot be walked;
- values trimmed to 200 characters.

The preview that was not what gets sent, the exact-match lineage, the flat 4000-token budget and the history truncation the user never saw closed in step 2, under a deterministic `BuildContext` and the request snapshot golden (`internal/service/testdata/request_snapshots/`, ADR 0035): every other fix here now shows up as a reviewable diff instead of a guess.

**3. The tool loop's limits and failure handling.** [R-tool-loop-14](ai-roadmap/tool-loop.md#r-tool-loop-14), [R-frontend-16](ai-roadmap/frontend.md#r-frontend-16), [R-provider-21](ai-roadmap/provider.md#r-provider-21).

The loop's own bookkeeping was fixed in the tier-0 pass and step 3: stale memory after a fix, the cap that cut the pagination hint, the six-iteration cap, a partial `<tool_call>` taken as the answer, marker instructions without schemas, fix tools advertised where they cannot run, missing panic guards and one deadline over both the decision and the apply ([Closed in step 3](#closed-in-step-3-the-tool-loop)). What is left sits beside the loop: Copilot's missing tool capability, slash commands with no link to the tools, and no `tool_choice`. `FakeProvider`'s failure modes and the prompt goldens from step 3 are the tests later loop changes land against.

**4. Approvals and applied fixes survive every ending.** [R-approvals-1](ai-roadmap/approvals.md#r-approvals-1), [R-approvals-7](ai-roadmap/approvals.md#r-approvals-7), [R-approvals-8](ai-roadmap/approvals.md#r-approvals-8), [R-approvals-10](ai-roadmap/approvals.md#r-approvals-10), [R-approvals-11](ai-roadmap/approvals.md#r-approvals-11), [R-frontend-9](ai-roadmap/frontend.md#r-frontend-9), [R-testing-14](ai-roadmap/testing.md#r-testing-14), [R-docs-5](ai-roadmap/docs.md#r-docs-5).

An approved fix changes the user's flow. Whatever happens next must not lose that change or misreport it: a Stop, a drain, a re-minted block id, a version conflict, a desktop restart, a read-only flow, a long journal. The thread keeps its flow and its context block across a fix (the tier-0 pass), and step 4 closed the Stop, the drain, the re-minted id, the version conflict and the desktop restart ([Closed in step 4](#closed-in-step-4-approvals-and-applied-fixes)). The backend's chat event goldens and the router-level approval table are the net that the card's next payload changes — a server deadline, a diff or a risk signal ([R-approvals-1](ai-roadmap/approvals.md#r-approvals-1), [R-approvals-7](ai-roadmap/approvals.md#r-approvals-7)) — land against.

**5. Settings and credentials that take effect.** [R-provider-22](ai-roadmap/provider.md#r-provider-22), [R-provider-27](ai-roadmap/provider.md#r-provider-27), [R-provider-28](ai-roadmap/provider.md#r-provider-28), [R-security-8](ai-roadmap/security.md#r-security-8), [R-observability-17](ai-roadmap/observability.md#r-observability-17), [R-docs-9](ai-roadmap/docs.md#r-docs-9).

In each case the UI or the API reports a state the server does not have. The deployment's `ai.*` writer (`PUT /api/admin/settings/ai`) and the device-flow refusal shipped in the tier-0 pass; step 5 closed the stored-as-sent `ai` section, the empty key that counted as "configured", the keyring outage that read as "no key", the unreadable key that read as configured and the silent rollback of a failed save ([Closed in step 5](#closed-in-step-5-settings-and-credentials-that-take-effect)). What is left here is the organisation credential routes, the credential lifecycle and the policy surfaces.

**6. Provider error classification and transport limits.** [R-config-5](ai-roadmap/config.md#r-config-5), [R-config-6](ai-roadmap/config.md#r-config-6), [R-docs-3](ai-roadmap/docs.md#r-docs-3).

Retry, the breaker, the watchdog and the user's error bubble all depend on how a failure is classified. Step 6 closed the hung upstream, the missing handshake bound, the header floor of the non-streaming fallback, the probe lockout, Gemini's body-first classification and the OpenAI-family 403 and quota misreads ([Closed in step 6](#closed-in-step-6-provider-transport-the-breaker-and-gemini)). What remains uneven:

- watchdog stops reuse `STREAM_STOPPED`;
- the client does not classify five server codes.

Unbounded resilience knobs ([R-config-5](ai-roadmap/config.md#r-config-5), [R-config-6](ai-roadmap/config.md#r-config-6)) set how far a misclassified failure can multiply.

**7. Token usage accuracy.** [R-observability-3](ai-roadmap/observability.md#r-observability-3).

Each item makes the recorded token counts differ from what the providers counted:

- retry drops a failed attempt's held usage;
- the fallback estimate omits tool schemas;
- usage rows can be dropped;
- a row's user is the chain's scope, not the one the call was for;
- rows carry no stream id or provenance;
- usage records are missing from the user data export.

They share `internal/ai/audited.go` and `retry.go`, and they are pinned by the same usage tests. This theme follows theme 6 because the attempt boundaries decide which usage exists to record.

**8. Rate limits and concurrency.** [R-frontend-c24](ai-roadmap/frontend.md#r-frontend-c24), [R-replicas-c23](ai-roadmap/replicas.md#r-replicas-c23).

With budgets out of scope, rate limits and stream caps are what bound AI use. Today:

- rate-limit refusals carry no wait time;
- the routes that call a provider are put on the AI rate-limit group by a hand-kept list;
- streams have no concurrency cap per organisation or per replica.

Step 8 closed the orphan answers, the leaked emit gate, the shutdown's cut answer write, the deletion of closed and evicted threads, the client half of the sidecar restart and the error bubbles re-sent to the model ([Closed in step 8](#closed-in-step-8-conversation-durability-and-the-turn-record)).
