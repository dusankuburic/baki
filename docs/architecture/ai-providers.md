# AI providers: the spec registry

A provider is described once, as an `ai.ProviderSpec` in `internal/ai/spec_<id>.go`, registered at init (ADR 0025). Every provider list is derived from `ai.Specs()` — the factory, the keystore keys, the embedding order, the listing, the catalogue route — and `internal/ai/testdata/providers.golden` pins the table: refresh with `go test ./internal/ai/ -run TestProviderSpecs_Golden -update-provider-specs` and review the diff. Never branch on a provider id by name: ask the spec (`Caps`, `Keys`, `Modes`, `Listing`); `TestArch_ProviderIDLiteralsOutsideSpecs` pins the literal count per file (only downward), and `TestArch_RegisterProviderOnlyInTests` keeps `RegisterProvider` out of production code.

Load-bearing spec fields: `Caps` (`chat`, `stream`, `embeddings` — with `EmbeddingIdentifier`, `tools`, `reasoning`, `model_aliases`, `live_listing`, `org_shared`, `prompt_cache`); `Modes` (the capability profiles the provider is offered in); `Egress` (`fixed_host`, `user_endpoint` — allow-listed and dial-guarded in the cloud profile — or `loopback`, never in the cloud profile); `Credential` (kind `api_key`/`oauth_device`/`document`/`none`, with typed `Fields` and `HelpURL`); `Keys` (the keystore rows: `Primary`, `OAuthToken`, `Family` for Azure resources); `Wire` (`anthropic`, `openai`, `gemini`, `responses`); `Resolver` (reads the credential when the rule is not "Keys.Primary"); `Ctor` (builds the raw provider); `Listing` (a `ListingHook` for a family whose state and models live outside the keystore — the Azure AI Foundry registry, installed from DI with `ai.InstallListing`). Copies that cannot import `ai` are pinned to the registry: `internal/config.EmbeddingProviderIDs` (`TestEmbeddingProviderIDs_MatchRegistry`), `core/models.DefaultSettings().AI.Providers`, the frontend's known set (the tolerant client renders unknown ids from the wire).

On the wire, `GET /api/providers/list` entries carry optional `caps[]`, `modes[]`, `credential{kind,fields[],helpUrl?}`, `color`, `icon`, `configurable`, and `GET /api/providers/catalog` (same policy) answers every registered provider of the running profile, configured or not, with its credential schema and per-kind `endpoints`. An id no spec describes is `PROVIDER_UNKNOWN` (400 on `/api/keys/*`, chat create and the context preview; 200 `{ok:false}` on `/api/providers/test`; the stream error code) — the codes are in [api-conventions.md](api-conventions.md).

## Adding a provider

1. A catalogue entry in `internal/ai/catalog.go` and a `spec_<id>.go` registering at init: `Caps` as the provider truly behaves (`TestProviderSpecs_Complete`), `Modes`, `Egress`, `Credential`, `Keys{Primary: id}`, `Wire`, `Ctor`, a unique `Order`.
2. A `Ctor` over an existing wire family (`openaiBase` for an OpenAI-compatible vendor) or a new provider file — which never spells its own id literal (the ratchet fails on it).
3. Refresh `providers.golden`; add a `core/models.DefaultSettings` row (a pin requires one); an embedding-capable provider also joins `internal/config.EmbeddingProviderIDs`.
4. A device-flow provider needs its auth routes; a family with its own registry adds a `ListingHook` installed from DI. A bare-key provider needs nothing else.
5. A `Resolver` (a provider that reads its credential itself, as Copilot reads its device-flow token, then its PAT) always reads the member's own keys: it is not given the factory's member/org rule. Such a provider therefore cannot be `CapOrgShared`; `mustRegisterSpec` panics on the pair and `TestProviderSpecs_Complete` fails on it. Without `CapOrgShared`, `ForOrg` and `ForEmbeddingOrg` fall back to the member's credential and `ForOrgCredential` reports `ErrKeyNotConfigured` before the Resolver runs. An org-shareable provider reads `Keys.Primary` under the rule (no Resolver); if one ever needs both, the `Resolver` signature must first take the rule and honour its org-only and org-first cases.

## Budgets and prices

There are none ([ADR 0037](../adr/0037-remove-ai-budgets-and-pricing.md)): the catalogue keeps model ids, windows and output caps, a usage row records tokens only, and nothing refuses a call for spend. Spend is read in the vendors' consoles and the Azure portal.

## Live smoke and evals

Every provider test in `go test ./...` runs on fixtures written from the vendors' documentation. Two opt-in suites ask the vendors themselves; both are built only with `-tags live` and gated per provider on `BAKI_LIVE_<PROVIDER>_KEY` — the provider id upper-cased with `-` as `_` (`BAKI_LIVE_CLAUDE_KEY`, `BAKI_LIVE_GITHUB_MODELS_KEY`), holding what the keystore would hold: the API key, the PAT or token (GitHub Models, Copilot), or the JSON credential document (`BAKI_LIVE_AZURE_FOUNDRY_KEY`, `BAKI_LIVE_LOCAL_KEY`). An unset variable skips that provider's subtests, so without keys both suites pass having called nothing. `BAKI_LIVE_<PROVIDER>_MODEL` overrides the model; the default is the provider's cheapest tool-capable catalogue model (`internal/testutil/live.go`), else its own default. The harness applies the desktop egress profile (`egress.AllowLoopback`), so a local server can be smoked too.

- **The smoke** (`internal/ai/live_smoke_test.go`, `go test -tags live ./internal/ai -run TestLive -count=1 -v`): per configured provider, through the factory's own chain (`ProviderFactory.For`, retries off), it lists the models, runs one `Chat`, one `Stream` offered `search_flow` with a prompt that forces the call, and one `Embed` where the spec has `CapEmbeddings`. It asserts invariants, not text: exactly one terminal chunk; usage above zero on the answer or carried on the error (the audited wrapper recorded a non-zero usage row); the tool call names `search_flow`, has an id and an input that is valid JSON with a `query`; the served model is reported; the cache counts fit inside the input. New entries in the repair memos (the parameters `send` repaired per deployment, the deployments that refused streaming — model names only, no endpoint) are logged and listed in the summary: a vendor change the fixtures do not show yet.
- **The evals** (`internal/service/chat_eval_live_test.go`, `go test -tags live ./internal/service -run TestLiveEval -count=1 -v`): the cases of `internal/ai/testdata/evals/` asked of each configured model through the real stream and graded as the offline replay grades them ([testing.md](../testing.md#internalservice)); prints a pass rate per model and each failing case's failed checks as want/got. A measurement: it fails only below `BAKI_LIVE_EVAL_MIN_PASS` percent (default 0). `-record-evals` rewrites the transcripts of the cases a native-tool model passed (one provider per run; review the diff).

**The cap.** Budgets and pricing left the product ([ADR 0037](../adr/0037-remove-ai-budgets-and-pricing.md)), so the run's hard cap is in tokens and calls, not dollars: `testutil.LiveBudget` clamps every call's `MaxTokens` (64 in the smoke, 1024 in the evals) and refuses every call once the run has used `BAKI_LIVE_SMOKE_MAX_TOKENS` (default 40 000, input + output as the providers report them) or made `BAKI_LIVE_SMOKE_MAX_CALLS` calls (default 40); the evals have `BAKI_LIVE_EVAL_MAX_TOKENS` (default 400 000) and `BAKI_LIVE_EVAL_MAX_CALLS` (default 100) per provider. A model that thinks by default (`testutil.LiveReasoning`: the service's `ai.ReasoningOutputFloor` list plus `grok-3-mini`) counts its reasoning against the same cap, so its calls get `testutil.LiveReasoningAllowance` (1024) on top and the effort pinned to `low` — instead of the service's 16 384-token floor, which would make the ceiling meaningless; a call that still stops at its cap is reported as such, whatever the wire calls it (`length`, `max_tokens`, `MAX_TOKENS`, `max_output_tokens`: `testutil.LiveTruncated`). The smoke is three calls per provider plus at most a provider's own parameter repairs; the evals' chain makes one attempt per call (no retries). No usage row reaches a database: the smoke's chain records into memory, the evals' chain has no recorder.

**The workflow.** `.github/workflows/ai-live-smoke.yml` runs both nightly and on `workflow_dispatch` (inputs: a provider regex, evals on/off). It is non-gating — never on push or pull request, required by nothing — and reads the keys from repository secrets of the same names (models from repository variables). The job summary lists pass, FAIL or skip per provider and step, the new repair-memo entries, the smoke's spend and the eval pass rate per model. No log is uploaded — GitHub masks a secret only in the console and only as a whole value, never a substring of the Azure credential document, never in an artifact — and the console output is scrubbed of URLs; the tests pass every failure message through `LiveProvider.Redact` (the key, the credential document's secret, id and endpoint fields and their hosts, every URL). The job goes red when the smoke fails.
