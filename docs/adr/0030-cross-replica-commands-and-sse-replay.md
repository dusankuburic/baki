# 30. Cross-replica commands and SSE replay

Date: 2026-10-13. Status: accepted (SSE half: fan-out, event ids with `Last-Event-ID` replay, subscriber presence; the stream command channel is ADR 0033).

## Context

`api.EventManager` was an in-process hub: an event emitted on replica A never reached a client on B; the chat watchdog (`HasSubscriber` every 15 s, cancel after two misses) killed a stream whose owner's tab sat on B after ~30 s; SSE carried no event ids and `Last-Event-ID` was ignored, so a reconnect lost what was emitted while disconnected.

## Decision

All of it sits behind `api.EventFanout` (`*redisx.SSEBackplane` is the one implementation); without the shared Redis the manager is byte for byte what it was.

1. **Fan-out.** One channel `baki:sse:ev` (declared `sse.emit`) with an origin filter (every message carries the publishing replica's instance id; a replica drops its own). `EmitTo`/`EmitToOrg`/`EmitToAll` deliver locally first, then queue (bounded 1024 messages / 16 MiB, one sender, never blocks; a full queue drops and counts `pad_sse_fanout_total{publish,dropped}`). `EmitToOrg` resolves the roster at the origin and publishes the user list. A receiver validates (unknown version/kind, empty/oversized (>256 KiB)/line-breaking body, a non-stream id, no audience → counted `ignored`, dropped), delivers via its own `offer` path and never publishes; the id is written into the frame only after `ValidStreamID`. Chat chunks, heartbeats and progress ticks are publish-only and ephemeral (no id, not logged, published only for users another replica holds — `PeerHint`, a cache read, one bounded 200 ms read for an unseen user; unknown counts as not held, recovered by the client's resume by offset). Everything else is durable and published unconditionally.
2. **Event ids and replay.** A durable event is appended, before delivery, to `baki:sse:log:<user>` (Redis Stream, `MAXLEN ~ 200`, key expiring 5 minutes after the last write; declared `sse.log`); the `XADD` entry id (`<ms>-<seq>`) is the frame's `id:` line on every replica. The write is one pipelined round trip bounded to 250 ms, skipped while Redis is degraded. An org event is copied into each member's log (≤256 members); `EmitToAll` carries no id and nothing tenant-scoped may use it. A frame over 32 KiB is not logged (delivered whole, no id). `HandleEvents` reads `Last-Event-ID` (an invalid value ignored and counted), registers the stream first, then replays `(id, +]` — at most 200 entries, none older than 5 minutes, oldest first; a live frame also in the replay is dropped. A Redis failure continues without a replay. The log key is the authenticated user's, never derived from the header. **A replay is complete or says so:** on more than 200 frames after the cursor, a cursor older than the log's first entry or than the 5-minute window, or an unreadable log, the server writes one `replay:gap` event (`{"name":"replay:gap","data":{}}`, carrying the newest log id so the gap is not replayed again) and the client refetches; an older client ignores the unknown name.
3. **Subscriber presence.** `baki:sse:subs:<user>` (declared `sse.subs`) is a hash: field = instance id, value `{n, exp}`; rewritten when a user's local stream count changes and every 15 s; valid 45 s; hash expires 60 s after the last write. `HasSubscriber(user)`: local streams answer without Redis; otherwise one `HGETALL` (200 ms, cached 5 s per user) counting another instance with `n > 0` and unexpired `exp`. **A Redis error or degraded state returns true** — a stream is never cancelled because presence is unreadable.
4. **Replica identity:** the name a replica goes by in Redis is `PAD_INSTANCE_ID` plus a boot suffix (`pod-7#3f9c0e`, `redisx.BootOrigin`), so two replicas sharing a `PAD_INSTANCE_ID` remain distinct (it is the SSE origin, the subscriber field, the snapshot owner and the command address).
5. **What crosses Redis:** event bodies in plaintext (every tenant's events to every replica; up to 200 frames × 32 KiB per active user for 5 min) and user ids in key names — a multi-replica deployment keeps Redis on a private network, requires AUTH, uses TLS (`rediss://`), and does not enable RDB/AOF persistence on the backplane instance; the app warns once at boot with `PAD_MAX_REPLICAS > 1` on a `redis://` URL or one without a password.
6. **Per-user caps across replicas (close-out):** with several replicas configured the caps hold deployment-wide via `redisx.SlotCap` sorted sets (10 event streams `sse.conn-slots`/`baki:sse:conns:{user}`, 10 WebSockets `ws.conn-slots`, 3 uploads `flow.upload-slots`): a member per held resource scored by lease end, rewritten every 10 s, a crashed replica's slots stop counting within 30 s, judged on the server's clock (`TIME` in the scripts). The local cap stays in front; Redis not answering admits on the local cap alone (fail open, `pad_redis_caps_total{cap,outcome="open"}`).

## Consequences

With Redis, an event reaches any replica's client, a stream is not cancelled for a tab elsewhere, and a reconnect replays up to 200 durable frames from 5 minutes. Redis holds bounded, volatile data only (every key has a TTL). Metrics: `pad_sse_fanout_total`, `pad_sse_log_total`, `pad_sse_replay_total{outcome}` (gains `gap`/`cut`), `pad_sse_replay_frames_total`, `pad_sse_presence_reads_total`. Mixed versions: a previous-release replica shares no channel and is an island — **the first Phase 5b deploy stays at one replica**; `maxReplicas` rises only when the whole fleet runs this release. Rollback is additive (expiring keys only, no migration); the client sends `Last-Event-ID` only after a server sent an id (CORS allows the header).
