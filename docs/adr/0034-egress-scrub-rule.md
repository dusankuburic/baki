# 34. The egress scrub rule

Date: 2026-10-24. Status: accepted, implemented (AI roadmap step 1).

## Context

Secrets reach the assistant's providers through many channels: flow properties and headers, comments, finding metadata, selected source files, the question and the history, organisation guidelines, tool results, fix previews, provider error text, and the knowledge base's own uploads and queries. Each channel scrubbed itself at its call site, and two fallbacks failed open: a document whose redacting clone could not be made was used as it was, and so was the post-fix document the tools read. No test looked at what actually left the process, so two channels (`Block.Name` of IF/SWITCH/CASE/LOOP headers and comments; pasted PAD code in messages, whose literal syntax the regex pass does not see) leaked until the roadmap's review found them.

## Decision

1. **The rule.** Every string the model can see passes the scrubber before the provider boundary, and nothing fails open: a clone that cannot be made is an error for the turn (`CONTEXT_UNAVAILABLE`, nothing sent) or, after an applied fix, leaves the tools on the previous clone with a note to the model (`toolDocSwap`). Knowledge documents are scrubbed at ingest and on re-index, conversations at rest (`normalizeConversation`), so the stores hold what the provider saw.
2. **Four scrubs, one table.** `ScrubText` is the regex pass over the secret-class table (`core/ai/scrubber/classes.go`), which also drives the stream scrubber that masks the answer as it streams. `ScrubDocument` masks a parsed flow: action fields, credential-named keys, `SET` literals, the `Name` of every block kind that keeps raw text (headers judged by the variable they compare, `%Creds.Password%` included; comments by entropy), then the regex pass. `ScrubSourceText` masks the same values in a source file. `ScrubFreeText` is for text without a parse — a chat message, the history, the embedding query, an uploaded runbook — and runs the regex pass first, then PAD's line rules (`SET … TO`, `<key>:` of a credential or of a sensitive action's field, condition and loop headers, `CASE` under a credential `SWITCH`, a `#` comment's opaque words) and the entropy check on PAD-shaped literals; it is idempotent on its own output (both passes judge the same literal text), which the stored conversations and the history memo rely on, and linear in the text.
3. **Enforcement.** The canary test `internal/service/chat_egress_test.go` plants one unique secret per channel in a fixture flow and runs a plain stream, the tool loop and the prompt loop against the capturing fake provider: no canary may appear in any `ai.Request` or any SSE event. `testutil.FakeProvider{RequireScrubbed: t}` fails any chat test whose outgoing request holds a string `ScrubText` would change, so a new path that forgets the scrubber fails where it is written. A channel is added to the canary list when it is added to the product.

## Consequences

A leak is a failing test rather than an incident; the per-call-site scrubs stay, since each knows its input's shape, and the egress test is the net under all of them. What is deliberately not done: a second scrub at the provider boundary. The boundary sees tool protocol (JSON arguments, ids, the `<tool_call>` markers) and prose alike and cannot tell a value from a key, so it would mask ids and schemas and still miss PAD's shapes; the shape-aware scrubs at the sites plus the canary give more coverage than a blind pass there would. Costs: a message is scrubbed once more at rest (memoised per scope), an upload once before chunking, a re-index page once per chunk. False positives of the scrubber are now permanent in the stored thread and corpus; the classes are kept conservative for that reason, and `ScrubFreeText` reads a single-quoted literal only on a PAD-shaped line.
