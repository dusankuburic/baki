# 29. Redis payload envelope, key registry and health policy

Date: 2026-10-13. Status: accepted, implemented (Phase 5b, wave 0).

## Context

Redis is optional (five mechanisms use it when set). Before this ADR no payload carried a version (a rolling deploy puts two releases on the same keys), one reader deleted presence records it could not decode, keys were scattered literals under four naming schemes with no TTL list, a Redis outage took every replica out of rotation via `/readyz` and could block a restart, and nothing refused `PAD_MAX_REPLICAS` above 1 without Redis.

## Decision

1. **A payload envelope** `redisx.Envelope{V int, Kind string}` (`{"v":1,"kind":"ws.room",...}`). Additive only: a field is never renamed or retyped; missing `v` is 0 (the pre-envelope shape) and always accepted. `redisx.Decode(kind, maxVersion, payload, dst)` returns `ok`/`unknown` (newer version or other kind)/`bad`, counts `pad_redis_msgs_total{kind,result}`, and leaves `dst` untouched unless ok. Unknown payloads are ignored, never an error to the sender; **a reader never deletes a record it cannot decode** — records are pruned by their own expiry only. Applied to the room message (`ws.room`), the presence record (`ws.presence`) and the resume snapshot read (declared v0; an unknown version is a miss and stays in place). The revocation message stays v0 on purpose (an old replica must act on it; the 30 s Postgres reload is the backstop).
2. **A key registry:** `redisx.Declare(Spec{Name, Kind, Pattern, TTL, Version, OnDown, Owner})` at package level; the owner builds names only through the declaration. `Declare` panics on malformed/duplicate specs, a missing on-down behaviour, a key without a TTL (every kind but pub/sub needs one — the server runs `volatile-lru`) and a channel with one (or a channel name under 8 bytes, which go-redis cannot report ready). `internal/di/testdata/redis_keys.golden` lists every family; archtest ratchets pin the declaring files and forbid literal key prefixes elsewhere. Shipped names are never renamed (`ws:room:`, `ws:presence:`, `chat:resume:`, `ratelimit:`, `baki:auth:revoked`); new families go under `baki:`.
3. **Previous-release fixtures** in `internal/redisx/testdata/redis/prev/<release>/` are decoded by tests each release; `TestPrevFixtures_EveryFileIsDecodedByATest` fails on an unused fixture.
4. **Health: degraded, not unready.** `redisx.Health` watches the client (ping every 5 s plus a go-redis hook on every operation): one failed ping or three failing operations degrade; any success recovers. `/readyz` stays 200 and adds `"degraded":["redis"]`; the database and blob checks still gate it; the signal to alert on is `pad_redis_up == 0` (gauge absent without Redis), with `pad_redis_errors_total{mechanism}`. Boot tolerates an unreachable Redis (WARN, starts degraded); a URL that does not parse still refuses to boot.
5. `PAD_MAX_REPLICAS` above 1 requires `PAD_REDIS_URL`, refused by config validation in every mode.
6. Rate-limit groups are frozen: `route.RatePerUser = "peruser"` sits with the group constants, the chain builds from them, `ratelimit_groups.golden` records each group's metric label and key shape (`ratelimit:{group}:{addr}`). Renaming a group in a two-release fleet splits its buckets and orphans its series.
7. Failure modes (Redis down): rate limit — per-replica in-memory bucket at the same rate/burst (the limit becomes N× for the outage); WS room fan-out and presence — open, local delivery unaffected, roster shows this replica only; chat resume — open, `Save` retried, `Load` a miss (another replica answers `STREAM_NOT_FOUND`); revocation fan-out — closed: a miss goes to Postgres, an error there means revoked (peers learn within 30 s); `/readyz` stays 200; boot starts degraded.
8. **Evictions (addendum).** Every key has a TTL so `volatile-lru` can evict any key silently: an in-flight budget ledger eviction makes the next check on that replica fail closed once (`AI_BUDGET_UNAVAILABLE`, `pad_ai_ledger_errors_total{op="lost"}`); an evicted resume snapshot makes cross-replica resume answer `STREAM_NOT_FOUND` (never an ok that stopped nothing); an evicted pending approval makes cross-replica decisions 404 until it times out. `redisx.Health` polls `INFO` and exports `pad_redis_evicted_keys_total` (WARN naming it) and checks `maxmemory_policy` once (warns on `allkeys-*`). Operators: run `volatile-lru` (or `noeviction` on a small dedicated instance), size `maxmemory` with headroom (SSE logs are the large tenant: up to 200 frames × 32 KiB per active user for 5 min). `HSET`+`EXPIRE` and `XADD`+`EXPIRE` pairs go out in one `MULTI`/`EXEC` so no key can lack a TTL; Redis failure log lines are rate-limited (`redisx.LimitedWarn`) and carry the error's class, never its text.

## Consequences

A rolling deploy is safe in both directions (old readers ignore the extra fields; new readers accept v0 and never delete what they do not know). A Redis outage no longer removes replicas from rotation or blocks a restart — a deployment relying on readiness must add the `pad_redis_up` alert. `pad_redis_msgs_total{result="unknown"}` rising during a rolling deploy is expected; `bad` rising is a producer bug. Rollback is additive: nothing renamed, no migration, no flag for the old boot behaviour.
