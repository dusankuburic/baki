# 28. AI budget as a pre-call hook, and a provider policy at the factory

Date: 2026-10-10. Status: accepted, implemented (Phase 4b, budget wave). The budget half and the in-flight ledger addendum are superseded by [ADR 0037](0037-remove-ai-budgets-and-pricing.md) (2026-10-24); the provider policy stands.

## Context

The daily AI budget was enforced by two callers of the provider chains (the chat service, the knowledge base); every other billed call was ungated — the provider connection tests and the per-turn query embed — and nothing pinned that a new caller would be. The only provider policy was the deployment-wide `Enabled` flag, read after the provider was built (its key already read); organisations could not say which providers may see their flows and corpus.

## Decision

1. **A pre-call hook in the audited wrapper.** `ai.BudgetChecker` (`Check(ctx, BudgetCall{Scope, OrgID, ProviderID, Model, Kind})`) is consulted first in `Chat`, `Stream` and `Embed` of every chain the factory builds — above the circuit breaker and retry, so a refusal is never retried — via `ai.WithBudgetChecker` on `NewProviderFactory`. The error is returned unwrapped (`errors.Is(err, service.ErrAIBudgetExceeded)` keeps classifying); wire codes unchanged (`AI_BUDGET_EXCEEDED`/`AI_BUDGET_UNAVAILABLE`, 429 `BUDGET_EXCEEDED`/503 `BUDGET_UNAVAILABLE`). Alias-model providers (Azure Foundry) are exempt (neither priced nor counted).
2. **Who is charged is resolved once** (`ai.WithBudgetScope(ctx, scope, orgID)`, defaulting to the request's org, else the shared credential's org); the knowledge base seeds it per run, so an org corpus embedded through a member's key is gated on the org and its usage row names the org.
3. **One usage read per request:** `ai.WithBudgetMemo(ctx)` is a request-scoped memo of daily-usage reads; the chat worker and each knowledge run seed one, so the turn's checks, the hook and the RAG query embed share one `GetDailyUsage`.
4. Chat keeps its two checks (start check before RAG and before the user turn is persisted — "no spend on refusal"; loop re-check). The hook is the net under them and the only gate for everything else.
5. **The ledger is a seam.** `AIBudget` holds a `spendLedger` (`memLedger` = the `sync.Map`); a ledger that cannot answer fails the check closed with `ErrAIBudgetUnavailable` (the "Redis down → budget fails closed" rule Phase 5b needs, pinned now).
6. **A provider policy before any key is read.** `ai.ProviderPolicy.Allowed(ctx, scope, orgID, providerID)` is consulted by every factory builder (`For`, `ForEmbedding`, `ForOrg`, `ForOrgCredential`, `ForEmbeddingOrg`, `ForAzureConnection`, `ForAzureConnectionEmbedding`) before the credential is resolved. `service.ProviderPolicy`: the deployment `Enabled` flag always, plus the organisation's allowed-provider list for any build naming an org — a personal builder on an org flow still names the flow's org, so org content goes only to admitted providers. An unreadable org settings document is its own error, never "allowed".
7. **The org allowlist** is `AI.AllowedProviders []string` (`allowedProviders`, omitempty) on the org settings document — additive, no version step. Empty allows every provider the deployment offers. The org settings route replaces the list only when the body names `ai.allowedProviders` (explicit `[]` clears it) — a partial write (the Rules panel posting `{analysis:{rules}}`) must not wipe the policy. Every listed id must be a registered provider (400 `PROVIDER_UNKNOWN`, `details.providers` naming the unknowns).
8. **Codes.** `PROVIDER_NOT_ALLOWED` on the stream's error event (policy copy naming the provider), as `ProviderTestResult.code`, 400 on the knowledge routes and context preview; the deployment disable folds into it. A policy that could not be read is `PROVIDER_POLICY_UNAVAILABLE` (503 / result code), never "not configured". Metrics: `pad_ai_budget_refusals_total{provider, call, reason}` (call: chat/stream/embed/build; reason: exceeded/unavailable/not_allowed), `pad_usage_dropped_total{reason}`.

## Consequences

Every billed call in the process is gated as long as it builds through the factory (chains built around it, like the Azure probes, carry no checker — they make no billed call by design). Rollback: no migration; the previous release keeps `allowedProviders` through `settingsdoc`'s merge-on-write and enforces it again on roll-forward — the hazard is a partial write by a release that declares the field, which is why this release's org settings route keeps the stored list unless the body names it.
