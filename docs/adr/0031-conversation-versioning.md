# 31. Optimistic versioning of persisted conversations

Date: 2026-10-13. Status: accepted, implemented (Phase 5b, multi-replica).

## Context

A conversation is one row (`conversations (flow_id, scope, messages JSONB)`) and every writer replaced the whole list via a blind upsert. An in-process mutex serialised the server's own writers on one replica only: with several replicas, overlapping read-modify-writes erased each other's messages (two tabs on two replicas, the client's save over the server's answer, a clear racing a persist), and the client's save (`POST /api/chat/save`) was unguarded even on one replica.

## Decision

1. **A version on the row, assigned by the database.** Migration 0044 (expand) adds `conversations.version BIGINT NOT NULL DEFAULT 0` (a constant default — no table rewrite), a sequence `conversation_version_seq`, and a trigger `BEFORE INSERT OR UPDATE` setting `version := nextval(...)` whenever `messages` changes. The trigger (not an application `version + 1`) means the previous release's blind upserts still bump the version, making the step safe in a rolling deploy. One sequence for all rows (plus the insert trigger) prevents ABA after delete and re-create: a recreated row gets a number nobody had. The residual ABA is the legacy 0 ("missing" and "untouched since the migration" are both 0 and both mean create-or-replace-expected-0); an optional one-off batched backfill (`UPDATE ... WHERE version = 0` with `nextval`) removes it sooner. An update leaving `messages` unchanged keeps the version.
2. **Storage.** `ConversationStore` gains `LoadConversationVersioned` (missing is `[]` at 0), `SaveConversationIf` (compare-and-swap via `UPDATE ... WHERE version = $expected RETURNING version`; create-with-0 is `INSERT ... ON CONFLICT DO NOTHING`) and `DeleteConversationIf`; a stale expectation returns `ErrConversationConflict` (wrapping `ErrVersionConflict`, mapped to 409). The old three methods stay for the migrator. Contract scenarios run on Postgres and the fake.
3. **`ChatService.mutateConversation` for the server's writers:** loads with the version, applies an idempotent function, saves with the swap, on conflict reloads and re-applies up to 5 rounds with 10-50 ms jitter, then gives up (logged, `pad_chat_persist_giveups_total`; the stream goes on). The in-process mutex stays as a queue (one contender per replica), not the correctness mechanism.
4. **API.** `POST /api/chat/get` returns `version`; `POST /api/chat/save` and `/clear` take an optional `baseVersion` — when present the write happens only at that version; stale answers 409 `CONVERSATION_CONFLICT` with `details.version` and writes nothing. **Without `baseVersion` the save stays the blind replace it was** (old clients) and is counted in `pad_chat_blind_saves_total`, so the contract step (making `baseVersion` required) can be scheduled when it stays at zero.
5. **The version leaves with the stream (addendum).** The server-owned turn's answer is stored at the emit of `done`, and `done`/`error` carry additive `conversationVersion` (after the answer write) and `conversationBase` (the version the question write read) — sent only when the two server writes were adjacent; otherwise the client keeps its own version and the next write reconciles. The client adopts only from the right base (`adoptStreamVersion`); `mergeHistory` keeps the server-trimmed head in front; the reconcile retry is a bounded loop (≤3 rounds) that ends quietly adopting the server's version; a re-sent turn keeps its question's id; a user turn already stored is written once. `pad_chat_conversation_conflicts_total{source=client_save|client_clear|retry|retry_exhausted}` counts every lost swap (`retry_exhausted` = a lost answer).

## Consequences

The lost-update windows of the server's writers and the versioned client writes are closed; blind saves (old clients) remain racy, now visibly counted. The client's save after a server-owned turn that it cannot adopt conflicts by design and costs one reload (the server already holds every message). A conflict exhausting five rounds loses the turn it was writing (needs six writers inside one read-write window). Rollback: expand step, no data change; the previous release ignores the column while the trigger keeps bumping it; `bakicli migrate down 43` drops trigger, function, column and sequence. An old client sends no `baseVersion` (blind, counted); a new client against an old server gets no version back and saves unconditionally.
