# 35. One request assembly for the turn and the preview, pinned by a snapshot

Date: 2026-10-24. Status: accepted, implemented (AI roadmap step 2).

## Context

What a model receives for a flow was assembled in several places: `BuildContext` wrote the flow context, `buildStreamRequest` added the history and the question, the tool loops attached the tool definitions or appended the marker-mode instructions after the first window check, and `PreviewContext` rebuilt a different subset — no analysis report, no history, no tool schemas, a token estimate over three strings — so the "Preview context" modal was not what the turn sent, under-reported on long threads, and with a cached report warmed another cache entry than the send. `BuildContext` ranged over four Go maps, so two builds of one request could differ byte for byte, which made a golden of the assembled request impossible, and the window check dropped the oldest turns without a word to the user. The context budget was a flat 4000 tokens whatever the model's window. The selected block's `Variable History` section existed and was never filled.

## Decision

1. **One assembly.** `ChatService.assembleTurnRequest` builds a turn's `ai.Request`: the memoised scrubbed context, the scrubbed history and the question in their data frames (ADR 0036), the generation parameters and, when the turn uses tools, the gate's tool definitions (a provider with function calling) or the marker-mode instructions appended to the system prompt. `buildStreamRequest` runs it and then the window check; `PreviewContext` runs it over the same inputs the stream resolves — the cached analysis report (`currentReport`), the stored conversation when the request carries none, the actor's tool gate — and reports the result: the system prompt as sent, the context text, the turn less the context frame, the window check's own estimate by part (system, context, history, tools, user), the history messages forwarded and how many the window would drop, the tools offered and the effective context budget. The preview and the send therefore share one `chat.context` entry. The tool loops still attach the tools or the instructions when handed a request that lacks them (tests build such requests), never twice.
2. **Deterministic context.** `BuildContext` lists finding metadata, block properties and the variable history by key, and the Analysis Summary by count descending then title; `ContextRequest.Provider` is gone and the Flow Overview decision and the final cut count with the same tokenizer (`contextTokens`). A selected block's `Variable History` is filled from the redacted clone (its output variable, then the variables it references, five at most, ten events each shown with the total). A source file's code fence is longer than any backtick run inside it.
3. **The snapshot.** `internal/service/chat_request_snapshot_test.go` runs the assembly over three corpus flows (`core/parser/testdata/samples`) × three tool gates (a chat-only token, a token with the write scope, a session with no approval applier) × two tool modes (native, marker), plus the plain stream and a "small" variant whose budget cuts the context and whose window sets the generation parameters, and compares the parameters, the offered tools, what the window check would drop, the system prompt, every history message and the turn in full with `internal/service/testdata/request_snapshots/<flow>_<gate>_<mode>.golden`, block and subflow ids renamed to their document order before the build (the parser mints UUIDs, whose token count would move the cut), CRs stripped. The fake provider counts len/4 and the budget is pinned by settings, so the cut is reproducible. `-update-request-snapshots` rewrites the goldens and deletes those whose variant is gone; the diff is reviewed.
4. **The derived budget.** Without a per-provider `ContextTokenBudget` the budget is `max(4000, min(128000, (window − 4000) / 4))` of the model's window, at most half the window (`derivedContextBudget`); an explicit setting still caps it; the budget is in the context cache key, so the preview and the send derive the same one. A selected source file is still cut to at most 16 000 tokens × 16 bytes before the AST scrub and the tokenizer see it (`maxSourceTokenBudget`), whatever the budget.
5. **History truncation is announced.** The window check reports where the current turn moved to; the turn emits one journaled `notice` event `{kind: "history_truncated", dropped, keptFrom}` before the first chunk (a provider with an exact token counter can add a second one from the loop's first iteration, still before any chunk), and one more for each tool-loop iteration that drops more; `keptFrom` counts the forwarded history (rows with a role history may not carry are not in it). The client keeps `keptFrom` on the stream slot (the streaming bubble shows it) and on the committed message; the server keeps the cumulative count on the stream control and stores it on the persisted answer (`ChatMessage.Truncated`) — not from the journal, which may be trimmed; the bubble shows "Earlier turns omitted (n)" with the thread's Compact action.

## Consequences

A change to the prompt's text, section order, truncation priority, tool gating or framing fails the snapshot test and is reviewed as a golden diff, which every later step relies on. The preview is the turn: a difference between the two is a bug in one function. The system prompt had to stay under about 450 tokens for a 1024-token window (half of which the answer keeps) to go on working, which shortened its wording. Costs: the preview now reads the stored conversation and asks the knowledge base (under the turn's deadline), as the turn does; a large flow on a large window sends a larger up-front context (the retrieval tools already gave the model the rest), and a `chat.context` entry, still one unit of the 32, can hold a context of up to the budget — about 16 MB across the cache at the 128k cap. What is not done: the settings UI does not show the effective budget (the preview does); native tool results are not framed (they travel in the provider's tool-result channel, which ADR 0036's rule covers).
