# 27. Embedding identity on knowledge chunks, chunker version on documents

Date: 2026-10-10. Status: accepted, implemented (Phase 4b, RAG). Amended 2026-10-23: chunk text masked for secrets. Amended 2026-10-26: §3 says when the sample still runs, §9 records the cross-replica org lease.

## Context

Nothing recorded which model produced a stored vector: text-embedding-3-small and Azure ada-002 are both 1536 wide, so a corpus re-pointed to another model at the same width read "searchable" while every search missed. The only mismatch detector was a billed sample call; a re-index re-walked already-converted chunks; the per-org mutation lock was process-local.

## Decision

1. Identity per chunk, version per document: `knowledge_chunks.embedding_identity TEXT NULL`, `knowledge_documents.chunker_version INT NOT NULL DEFAULT 1` (0042, expand).
2. The stored identity is the provider's string, as reported, format frozen: `label|baseURL|model|dims` (OpenAI-compatible) and `gemini|model` (`ai.EmbeddingIdentity`, pinned by `TestEmbeddingIdentity_FormatFrozen`). A spec-derived identity must keep producing the same string or ship a stamped rename. The string is never parsed for width — `vector_dims` stays the width check.
3. NULL is legacy, matched leniently (`embedding_identity = $current OR IS NULL`, never worse than before). The billed sample guard is skipped only when every row carries the caller's identity (and, with pgvector, sits in the vector index). It runs for rows without an identity, and also for a corpus with stranded rows (under another identity): there it only tells another width (the stranded-corpus recovery) from another model at the same width, and a same-width stranded corpus is another model whichever rows the sample picked (`checkCorpusModel`). With pgvector it also runs when rows of the caller's own identity sit outside the vector index, to answer the width alone. When a sample proves the caller's model reproduces legacy rows, `StampKnowledgeChunkIdentity` rewrites the org's NULL rows, ending the lenient match per org.

   Amendment (2026-10-27, R-knowledge-3): the stamp is per document, never org-wide. When the caller's identity is known and the census shows legacy rows beside it (and none of another identity), the proof samples the legacy rows alone: the first and the last legacy chunk of up to `corpusSampleSize` documents that still hold legacy rows (`SampleLegacyKnowledgeChunkEmbeddings`), so each proof reaches documents not yet proven, and a re-index that stopped inside a document (which converts a prefix of it in id order) cannot hide its unconverted tail behind its converted head. The worst pair still decides. A proof stamps the caller's identity on the legacy rows of the documents it proved and no other (`StampKnowledgeDocumentIdentity`); documents outside the sample keep the lenient match until a later proof reaches them. Each stamp is recorded in the audit trail (`org.knowledge_identity_stamp`, Meta: identity, the proven document ids, the rows stamped). Consequences: a legacy corpus mixed beyond the sample is refused as soon as a proof reaches the other model's documents, instead of being labelled one model; an unforced re-index restarted after a forced one stopped samples the unconverted tail and is refused, so the tail is never stamped with the new identity. No un-stamp API: a forced re-index skips nothing and bypasses the guard. The identity format and the NULL-is-legacy rule are unchanged. Chunks of an unfinished two-phase upload (R-knowledge-2, v51) are neither legacy nor sampled nor stamped.

4. Writes carry the identity: `AddDocument` stamps every chunk and the document's `rag.chunkerVersion` (1; a geometry change bumps it and adds a golden). A re-index page is stamped with the identity it was embedded under.
5. Re-index walks only what is not at the caller's model: unforced, `ListKnowledgeChunkContents(..., notIdentity)` skips chunks already under the caller's identity; forced, every chunk is rewritten (an Azure deployment re-pointed behind the same name keeps its identity).
6. Precise empty-result classification via the identity census (`CountKnowledgeChunksByIdentity`): chunks under another identity count `pad_rag_stranded_search_total` (new); nothing at the configured width counts `pad_rag_dim_mismatch_total`; below the floor counts nothing.
7. A declared on-demand re-embed job, never automatic spend: `knowledge_reembed` (`lifecycle.DeclareJob`, derived key, on demand) runs `ReindexOrg` page after page as the admin who started it (RLS) under their credential scope. `POST /api/orgs/{id}/knowledge/reindex` with `{"background": true}` answers 202; refused 400 `EMBEDDING_ORG_NOT_CONFIGURED` unless the embedder resolved to the org's shared credential (`ai.UsedOrgCredential`) — a member's personal key is not spent unattended. One job for every org: its lease serialises runs (409 `KNOWLEDGE_BUSY`; 503 `KNOWLEDGE_JOB_UNAVAILABLE`). A detected model switch is counted and shown, never self-repaired.
8. Admin surface: `GET /api/orgs/{id}/knowledge` carries `embeddingStranded` per document and `chunkerVersion`.
9. Corpus mutations are serialised per org at two levels (amendment, 2026-10-26). `lockOrg` takes an in-process mutex, then, when the deployment has a `lock.Leaser`, a cross-replica lease (a session-level `pg_try_advisory_lock` on a pooled connection) held for one request: an upload request's guard, pending write and the pages it embeds, a continuation's pages, or a re-index request's page loop (since the two-phase upload, never across requests: between them a pending document is touched by nothing else, because re-index skips pending chunks, and each continuation takes the lease again and re-checks the model). The key is `rag.KnowledgeLockKey(orgID)`: high word `0x6b6e6f77` ("know"), low word FNV-1a-32 of `knowledge_org:<org id>`. The high word must never be 0 or `0xFFFFFFFF`, where the `hashtext` keys of the write transactions below land, or a lease would deadlock against its own operation's write. Both levels are non-blocking: an org already held answers 409 `KNOWLEDGE_BUSY`. A replica holds at most `PAD_KNOWLEDGE_LEASE_CAP` leases at once (default 4: `config.DefaultKnowledgeLeaseCap`, `rag.DefaultLeaseCap` for a service built without config), because each pins a pooled connection for the operation; the operation beyond the cap is busy too. A lease that cannot be asked for (the database does not answer within the 5 s acquire timeout) answers 503 `KNOWLEDGE_LOCK_UNAVAILABLE` and starts nothing, and a lease lost mid-operation cancels it, which answers busy. Beside the lease the synchronous writes keep the org's transaction lock (R2): `SaveKnowledgeChunks` and `UpdateKnowledgeChunkEmbeddings` take `pg_advisory_xact_lock(hashtext(org_id))` in their own transaction, which protects a single write when the lease is lost part-way. The operator's view is `docs/architecture/operations.md`.
10. Chunk text is masked for secrets before it leaves the deployment or reaches the store (amendment, 2026-10-23). `AddDocument` runs `scrubber.ScrubFreeText` (the regex pass plus PAD's literal syntax, since runbooks paste flow code) over the document text and the filename BEFORE chunking: the mask is then in the text every chunk is cut from, so neighbouring chunks carry an identical overlap and `stripOverlapPrefix`'s exact match keeps de-duplicating it — scrubbed chunk by chunk, a secret straddling the 150-rune overlap is masked in one chunk and left as a key-less fragment of the value in the next. A re-index page embeds the stored text scrubbed, each chunk read beside the other chunks of its document (a page that holds part of a document reads it whole): a chunk stored before this amendment and cut through a secret — the key in one chunk, the value carried into the next one's head — is scrubbed as the stretch of the document it came from, so the secret is matched whole in both, and the successor takes the masked predecessor's exact tail as its head, which keeps the overlap `stripOverlapPrefix` de-duplicates. The model guard's samples embed their stored text scrubbed on their own. `UpdateKnowledgeChunkEmbeddings` writes the vector and the identity, so such a chunk's stored text stays raw until its document is re-uploaded. `pad_rag_scrubbed_chunks_total{source}` counts the masked chunks at upload and on re-index pages; retrieved guidelines are scrubbed again when rendered into a turn, as before, and the Knowledge Base panel says uploads are masked.

## Consequences

Uploads into a stamped corpus and re-indexes of one no longer bill the sample call. Storage contract grows the identity filters and the census/stamp methods; `Knowledge_chunks_carry_their_embedding_identity` holds Postgres and the fake to the same rules. Rollback: expand; both columns ignored by the previous release. One hazard: a re-index run on the previous release during a rollback rewrites vectors without touching identities — if that happened, run `bakicli migrate down 42` before rolling forward, or force a re-index after it. Open: an Azure deployment re-pointed behind the same name is undetectable (the admin forces a re-index). Since the 2026-10-23 amendment the embedding provider sees no unmasked secret from the knowledge base and new uploads store none. A sample stored before it whose text changes under the scrub is compared from the masked text against a vector of the raw one: the same-model threshold absorbs a mask in a 1000-rune chunk, a chunk that is mostly secret may read as another model until re-uploaded. Open: a re-index that rewrites the stored text needs the embedding update to carry `Content`; until then a non-zero `source="reindex"` count names an org with documents to re-upload.
