# 37. Remove AI budgets and pricing

Date: 2026-10-24. Status: accepted, implemented. Supersedes the budget half of ADR 0028, the in-flight ledger addendum to it, the ledger keys of ADR 0029 and the pricing mode of ADR 0025.

## Context

Baki is an internal tool for the company's developers, hosted as one container on Azure. It carried a daily AI budget built for a multi-tenant product: a deployment-wide and per-user daily cap in USD, an in-flight spend ledger (in process, or in Redis across replicas) that reserved a maximum response per running stream, a pre-call hook in the audited provider wrapper that refused a call over budget, re-checks in every tool-loop iteration, a gate on knowledge-base embedding runs, and the error codes `AI_BUDGET_EXCEEDED` and `AI_BUDGET_UNAVAILABLE`. Under it sat a price for every model, typed by hand into the provider catalogue, an estimated cost on every usage row, cost rates on every done event, stored answer and resume snapshot, and cost fields in the dashboard and analytics answers.

Vendor prices change faster than releases, so the stored costs drifted from the vendors' invoices, and a wrong price either refused work that was within budget or let spend through. The cost was not shown anywhere in the product: the chat meter and the dashboard cards rendered token counts only. The owners decided an internal tool needs neither the cap nor the price table: the vendors' own consoles and the Azure portal are where spend is read.

## Decision

1. **No budget.** `AIBudget`, both ledgers (`memLedger`, `redisLedger`, `internal/redisx/inflight.go`), the audited wrapper's pre-call hook (`BudgetChecker`, `BudgetMemo`), the chat service's reservation and its per-iteration re-check, the knowledge base's run gate, the budget sentinels and their error codes are gone. The settings fields `dailyBudget`, `perUserDailyBudget` and `showCostEstimates` are gone from the settings model and the admin writer; stored documents that still carry them decode and drop them. `PUT /api/admin/settings/ai` keeps the embedding provider and model only, and the admin page's card is "AI embeddings".
2. **No price.** `ai.Pricing`, `ModelInfo.Pricing`, `Provider.PricePerMillionTokens`, the spec's `PricingMode` and the cache-read multipliers are gone; the catalogue keeps model ids, windows and output caps. A usage row records tokens, the provider, the requested and served model, the user and the organisation, and no cost. The done and error payloads, `ResumeResult`, the resume snapshot, the begin answer and stored chat messages carry no rates; a snapshot or message an older release wrote with rates still decodes, and the rates are dropped. The provider listings carry no price and no pricing mode. The dashboard home answer has no cost-by-provider section; the analytics AI section reports tokens and calls per day, provider and model, ordered by tokens.
3. **What stays.** Token accounting (the audited wrapper's usage rows and its no-usage estimates), the provider policy (ADR 0028's other half), the per-user stream caps and the rate limits. The context helper that names who a call is for is `ai.WithUsageScope`: it attributes usage rows and tells the provider policy the organisation. The policy's refusals are counted in `pad_ai_policy_refusals_total{provider}`, which replaces `pad_ai_budget_refusals_total`; `pad_ai_pricing_fallback_total`, `pad_ai_usage_estimated_cost_total` and the `pad_ai_ledger_*` metrics are gone, and so are the `baki:ai:inflight:*` keys.
4. **The column.** `usage_metrics.estimated_cost` stays in the schema for one release (its `DEFAULT 0.0` keeps the release before inserting); dropping it, with the two indexes that INCLUDE it, is a pending contract step in `internal/storage/database/migrations/README.md`.

## Consequences

Nothing caps AI spend inside Baki: a runaway loop is bounded by the tool-loop limits, the stream caps and the rate limits, and spend is watched in the vendors' consoles and the Azure portal (cost alerts there are the replacement for the daily cap). The two-replica smoke no longer has a budget scenario. Reintroducing a cap later means a fresh decision; this tree's history (the commit before this one) holds the removed design.
