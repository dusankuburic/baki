# 5. Secret columns are encrypted at rest with the keystore key

Date: 2026-10-07. Status: accepted. Amended 2026-10-10: key rotation.

## Context

Org notification channels kept their webhook URL and HMAC secret in plaintext `TEXT` columns; for Slack and Teams the URL is the credential, so any database dump handed out every org's channels.

## Decision

- The Postgres backend encrypts secret columns itself (`field_crypto.go`). Key: the keystore's (`PAD_ENCRYPTION_KEY`, legacy fallback `PAD_AUTH_SECRET`); a per-process secret never qualifies. Format: `enc:v1:` + base64(nonce ‖ ciphertext), with table, column and row id as associated data, so a ciphertext copied to another row or column does not decrypt. An idempotent once-per-boot job under a cross-replica advisory lock seals plaintext rows; plaintext rows stay readable until then. Sealed columns: `org_channels.url`, `.secret`, `.secrets`, `org_ci_credentials.secret`, `idempotency_keys.body`, and the keystore's `provider_keys.ciphertext`, `org_provider_keys.ciphertext`. Future secret columns use `sealField`/`openField`, join the backfill and `fieldSealedColumns` (the coverage test enforces the last).
- **Rotation.** `PAD_ENCRYPTION_KEY_PREVIOUS` lists replaced keys, comma-separated, newest first; each entry meets the current key's cloud rule (≥32 chars, not a placeholder, not low-entropy) and may not repeat the current key or itself. Reads try the current key, then each previous; writes always seal with the current key. No format change (`enc:v2:<kid>` rejected). Every boot with previous keys runs a background re-seal (`lifecycle.Bounded` `secret_reseal`, after the server, 30 min ceiling, one replica under advisory lock `bakikrot`), keyset-paged (500 rows a page, 64 for idempotency bodies ≤256 KiB), moving values via compare-and-set so concurrent saves are never overwritten. Unreadable values are counted, named by table/column/row (never the value) and left as stored. Completion line: `secret re-seal complete: every sealed value opens with PAD_ENCRYPTION_KEY`.
- **Operator procedure (rolling deploys only):** 1) keep `PAD_ENCRYPTION_KEY`, set `PAD_ENCRYPTION_KEY_PREVIOUS=<new>`, deploy; 2) set `PAD_ENCRYPTION_KEY=<new>`, `PAD_ENCRYPTION_KEY_PREVIOUS=<old>`, deploy; 3) wait for the complete line (`remaining` > 0: restart one replica; `unreadable` > 0: add the missing key or re-enter those secrets); 4) remove `PAD_ENCRYPTION_KEY_PREVIOUS`.
- **Secrets in configuration** are `secret.Value` (`internal/platform/secret`) in `config.Config` — `Auth.Secret`, `EncryptionKey`, `EncryptionKeyPrevious`, `SSO.ClientSecret`, `Server.MetricsToken`, `Storage.DatabaseURL`, `AzureBlobConnectionString`, `Redis.URL`, `Email.Password`, governance signing secrets, the Jira token, `InboundWebhookSecret`, the webhook URLs — printing as `[redacted]` in every form (`%v`, `%q`, `json.Marshal`, slog, wrapped errors); `Reveal()` is the only path to plaintext, used at the boundary needing it, never to log. Sources refuse the literal `[redacted]`, so a redacted log line pasted back as configuration fails at boot.

## Consequences

Without the key a process refuses sealed values (`ErrFieldKeyMissing`) rather than returning ciphertext as a URL. Rolling back to `PAD_ENCRYPTION_KEY=<old>` alone after step 2 makes the new key's values unreadable (`ErrSecretDecryptFailed`; users re-enter them). Safe undo: with this release rotate back, wait for the complete line, then deploy the older release. An unreadable channel is listed with `Unreadable` set (API `unreadable: true`), skipped by the scanner, tested with 400 `CHANNEL_UNREADABLE`; an edit entering the URL again reseals it.
