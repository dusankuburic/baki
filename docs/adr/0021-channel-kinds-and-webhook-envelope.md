# 21. Channel kinds are a registry, channel secrets are write-only, and webhooks carry a versioned envelope

Date: 2026-10-10. Status: accepted (Phase 4c).

## Context

Five notification kinds were known in ~twenty places with per-kind switches and hand-written builders; the org channel API wiped the HMAC secret on every edit, re-enabled paused channels, and put channel URLs (the credential for Slack/Teams) into WARN logs; the generic webhook body had no id, delivery id or schema version and its signature covered the body only, so a captured request verified forever.

## Decision

1. **A registry, one file per kind.** `internal/notify/kinds_<id>.go` registers a `KindSpec`: frozen `ID`, `Scope` (organisation/deployment), `Fields` (name, `Secret`, `Required`, `Check`), an `EgressSpec`, `Signed`, `Build`, `Public`. `Register` refuses an incomplete spec, a duplicate id, and a proxy-trusting egress without a host list. An org kind's fields beyond `url`/`secret` live in `org_channels.config` (public) and `.secrets` (sealed) — one pair of generic columns, so a new org kind needs no migration (expand migration `org_channel_fields`).
2. **Secrets stay in the row, sealed, and are write-only.** An edit keeps what it omits (secret, `enabled`, `name`, creation time); `"clear": ["secret"]` removes the secret. The URL is write-only for admins too: the list shows `host/…` (`notify.ListedURL`, deliberately scheme-less). An edit keeps the stored URL when `url` is empty or equals the current listing (with or without `urlUnchanged: true`); any other `url` containing the marker `…` (also `%E2%80%A6`) is a 400 `INVALID_CHANNEL`. Logs and errors carry only `scheme://host/…` (`RedactURL`, `RedactError`); the channel test answers 502 `CHANNEL_DELIVERY_FAILED` with `details.reason` on its own `channel_test` bucket.
3. **One egress answer per owner of the URL:** `egress.ForDeployment(capability.Set)` for org channels (with accounts `BlockInternal`, without `AllowLoopback`; private and link-local refused by both), used by saves, deliveries and the test. The deployment's own `PAD_NOTIFY_*` channels use `egress.ForOperator`. `PAD_NOTIFY_ALLOWED_HOSTS` (exact hosts or `*.suffix` globs, validated like `PAD_AZURE_FOUNDRY_ALLOWED_HOSTS`: no glob over a public suffix or multi-tenant hosting zone, no IP literal) narrows a kind's hosts: a target must be on both; enforced at save (400 naming the host, never the list), at every delivery, and in the client's `Proxy` hook before it dials.
4. **The envelope, v1 additive.** Every HTTP delivery carries `X-Baki-Event`, `X-Baki-Delivery` (same across retries), `X-Baki-Timestamp` (per attempt), `User-Agent: baki/<version>`; a signed kind adds `X-Baki-Signature-V2: sha256=<hex HMAC(secret, "<ts>." + body)>` and keeps the deprecated body-only `X-Baki-Signature`. The body adds `schemaVersion: 1`, `id`, `deliveryId` and `orgId` (org channels); `new_rules` events add `ruleIds` and `flowCount`. The event `id` is `evt_` + 24 hex of the inbox row id (alert) or notice id, so every channel, retry and replica sends the same id; `at` is stamped when raised.
5. **`new_rules` reaches the channels** once per notice, at the last flush of the sweep that inserted it: an org's notice to its channels, the deployment's to the deployment's; a user's notice reaches no channel.
6. **Jira's description is Atlassian Document Format.** Org `jira` fields: `url` (base URL), `email` (Basic-auth user), `token` (secret, required, write-only, never listed; `hasToken`), `project` (key). **Org `email`: `recipients` is a list of the organisation's user ids (≤50) whose address is verified** — never typed addresses (no relay for tenant text) and not roles; every delivery re-resolves ids to verified current members. Without an enabled mail sender the kind is not offered and an existing email channel is skipped.
7. **Per-channel event subscriptions.** `org_channels.events` (JSONB array, NULL) holds the event types a channel receives, chosen from `drift`, `health_regression`, `new_rules` (≥1; `analysis_complete` is the deployment's only); NULL is the default set (all three), frozen as before; an event type added later is opt-in. The scanner checks `notify.Receives` before taking a delivery slot.
8. **`teams-workflow` kind** (org and deployment, `PAD_NOTIFY_TEAMS_WORKFLOW_URL`): posts an Adaptive Card 1.4 with every text as a `TextRun` (never Markdown — a flow name is tenant text and would render as a link). Unsigned, https only, no kind host list (Logic Apps hosts vary; operators pin with the allow-list).
9. **The options route** `GET /api/orgs/{id}/channels/options` (org admins) answers kinds, events, defaults and `hostsRestricted`; the list itself only with `PAD_NOTIFY_ALLOWED_HOSTS_VISIBLE=true` (it may name other customers' hosts).
10. **An unreadable channel** (no configured key opens it) no longer fails its org's list: listed with `Unreadable`/`unreadable: true` and no sealed value, skipped by the scanner (WARN + error report by channel id), its test 400 `CHANNEL_UNREADABLE`, re-entered by an edit, deletable.

## Consequences

A new kind is one file. Admins no longer see a channel's full URL; tenant text never forms a link or mention in any chat format (Slack `&<>` escaped, cards `markdown: false`). Rolling back: rows are unchanged; the previous release wipes secrets on edit again, sends zero `at`, ignores `PAD_NOTIFY_ALLOWED_HOSTS`/subscriptions, skips unknown kinds at delivery (their tests 400) and cannot save org `jira`/`email` rows; the down migration drops the three columns and the org jira/email rows.
