# 16. Analyses record their rule set; new rules give a notice, preview rules never gate

Date: 2026-10-08. Status: accepted (core half wave 2; storage, scanner, notices and CLI baseline file in wave 3).

## Context

Baselines stored finding keys only and snapshots only scores, so a release adding or revising a rule made every new finding look like drift: a drift alert per baselined flow (fanned out to inbox, SSE, every channel, a Jira bug per flow) plus a health regression, repeated after every restart. Org rule toggles and custom-rule edits did the same.

## Decision

1. **One gating predicate.** `analyzer.Gates(f)` is false only for a finding stamped `Finding.Stage = "preview"` or of a rule that is a preview built-in in this binary (covers saved-older JSON); everything else gates, unknown stage or rule included (fail closed). Used by policy evaluation (preview findings counted in `PolicyResult.Preview`, never a violation; no opt-in), the health score, SARIF (`level: "note"`, `properties.stage`), JUnit, `GatingFindings`/`CountGating` for the bakicli exit code and the CI webhook. Preview findings stay in the findings list and `Stats`.
2. **A rule reference is `{ID, Rev, Stage}`** (`models.RuleRef`); a built-in's `Rev` is empty at Revision 1 and `r<N>` above, a custom rule's is its `MatchDigest()`. Severities and options are not part of a reference.
3. **A rule set** is a sorted, de-duplicated reference list with a digest (`models.RuleSet`, `analyzer.NewRuleSet`): `"rs1:"` + hex SHA-256 over each reference's three fields as length:bytes in order; the empty set is `rs1:e3b0c442…b855`; a new encoding needs a new prefix. `runAnalysisWalk` stamps `AnalysisReport.RuleSet = RecordRuleSet(enabledRules)` before caching (not serialized).
4. **"New" is set-based** (`NewRuleAge`): a rule is new when its current reference is absent from the recorded set (added rule, revision bump, matcher edit, promotion from preview). A record without a usable rule set is legacy: it saw every custom rule and built-ins with `IntroducedIn <= 1 && Revision <= 1`. Toward drift, the status quo wherever unclear: a finding whose rule the current set does not name is drift.
5. **Drift is split, not redefined.** `ComputeDrift` is unchanged (`New` = every finding not in the baseline); `SplitDrift(new, age)` partitions it into `Drift` (alerts), `NewRule` (one notice per scope and digest) and `Preview`. Regression compares like for like: the snapshot's score against `HealthOf` over the findings without those of the rules the snapshot's score did not count.
6. **Storage (0037, expand).** `flow_baselines` and `flow_analysis` gain `rule_set`, `rule_set_digest`, `rule_set_at`; a reader takes the set only while `rule_set_at` equals `created_at`/`analyzed_at` (the previous release's rows read as legacy). Single reads return the set (the API sends only the additive `ruleSetDigest`); batch reads return the digest only; `RuleSetsByDigest` resolves digests and is a system read pinned to the scanner. A failed digest read leaves the flow uncompared and unrecorded — never a fallback to legacy (could silence or flood).
7. **Scanner.** Drift alerts come from `SplitDrift(...).Drift` only. `InsertGovernanceAlert` reports whether the inbox row is new and only an inserted alert is dispatched — after a restart or failover nothing is re-sent. New-rule notes go to `rule_notices` (PK `new_rules|scope|scope_id|digest`; scope `org`, `user` or `app`; generated `user_id`/`org_id` cascade columns; RLS plus the app predicate `ruleNoticeVisible`) through `UpsertRuleNotices` (inserts new, merges known, returns inserted ids); only an inserted notice is announced once (SSE `governance:alert` `type: "new_rules"`). The retention sweep removes a notice no sweep touched within the audit window. The bell lists undismissed notices (at most 10) ahead of alerts; Clear deletes alerts only (a deleted notice would be re-announced by the next full sweep).
8. **CLI baseline file.** `-update-baseline` keeps writing version 1 (bare array of finding keys); the reader also accepts version 2 `{"schemaVersion": 2, "keys": [...], "ruleSet": {...}}`; a higher version exits 2. New stable rules keep gating against any baseline file; preview findings never gate. An unreadable or invalid baseline exits 2 before anything is written. With several path arguments each key is written `<path>#<key>` and each flow checks its own keys only.

## Consequences

A preview rule raises no drift, regression, notice, CI failure or health change; promoted to stable it is new to every record that saw it as preview. After this release the first sweep re-analyzes every flow and legacy baselines produce one notice per scope for the revised rules. A legacy health snapshot is not compared (its release graded differently); the skipping sweep records its own analysis as the snapshot. `flow_analysis` rows grow by ~1-2 KB JSONB. The report cache must fold stage and revision into its key (ADR 0017).
